# Games demand relative input, timelines and restraint

Video games differ from the desktop apps computer-use-mcp 7.7.0 was built for in four compounding ways: they read input below the layer the server writes to, they keep running while the model thinks, they draw interfaces no accessibility API can see, and many forbid automation by contract and police it with anti-cheat. First-person games integrate relative mouse deltas and per-frame key state, while the server sends only absolute pointer warps (`native/src/mouse.rs:946-954`), Windows virtual keys with `wScan: 0` (`native/src/keyboard.rs:1062-1075`) and 0 ms taps, and has no gamepad path at all; a screenshot-model-action round of three seconds spans about 180 frames at 60 fps; and the server's only default app gate is a list of credential managers (`src/session/legacy-policy.ts:126-128`). The field's answers split cleanly. Small trained policies (Lumine, SIMA 2, Game-TARS, NitroGen) emit relative deltas, held-key chunks or gamepad vectors at 5–30 Hz, while the frontier-model harnesses that finish games pause the game, read text state and call game-specific tools; on raw pixels in real time, frontier models complete under 2% of VideoGameBench ([VideoGameBench](https://arxiv.org/abs/2505.18134v2)). Unreal 5.8, Roblox Studio and Blender now ship official MCP servers, so for game developers the desktop server is the bridge, not the main route. The plan below therefore starts with restraint and truth (a protected-game gate that refuses input to anti-cheat titles and never disguises synthetic input, plus scan codes, press durations and multi-key chords that actually work), then adds reach (relative pointer motion on all three platforms, key-down/up timelines inside `run_steps`, a `game` profile, engine-API routing), then observation (frame bursts on a persistent capture stream, animation-tolerant waits, honest Windows full-screen and HDR capture, Windows OCR), and leaves gamepad output as an opt-in spike, because every virtual-pad route needs an archived driver, a restricted capability or an Apple entitlement.

## Games read input below the layer the server writes to

An ordinary app takes positions and characters from the window system and exposes buttons to accessibility APIs, which is what this server automates well. A game reads hardware-shaped state (relative motion, physical keys sampled once per frame, controllers) through focus-bound APIs. The table sets the two side by side against what 7.7.0 does today; the subsections give the platform evidence.

| Dimension | Ordinary desktop app | Typical PC game | computer-use-mcp 7.7.0 |
|---|---|---|---|
| Pointer | Absolute positions through window messages or accessibility actions | Relative deltas (Raw Input, `NSEvent`/`GCMouse` deltas, XI2 raw motion, `wp_relative_pointer`) with the cursor hidden and clipped | Absolute warps on every platform; points off every display refused (`native/src/mouse.rs:529-545`, `:946-954`, `:28-60`; `src/session/input-handlers.ts:792-799`) |
| Keys | Characters or virtual keys | Physical scan codes, state polled per frame | Windows `wVk` with `wScan: 0`; no numpad or right-hand modifiers; `w+a` presses only `a` on macOS, Windows and X11 |
| Press timing | Any down/up pair registers | A pair inside one 16.7 ms frame can vanish | 0 ms taps and clicks; `hold_key` up to 10 s; no duration on `key` or `click` |
| Controllers | None | XInput, GameInput, GameController pads with analogue sticks | None, and the guard cannot see a person's controller |
| Background | Accessibility and pid delivery work on covered windows | Input is focus-bound; many games pause in the background | macOS-only pid delivery, which hardware-reading apps ignore (`src/session/pid-delivery.ts:1-14`) |
| Display | Composited window | Exclusive fullscreen, HDR, DPI-unaware stretching | Capture ladder never tested against a game |
| UI semantics | Accessibility tree | Self-drawn; tree empty unless the game opts in | OCR on macOS only (`src/tool-catalog.ts:255-258`) |
| Clock | Waits for the user | 30–120 fps regardless of the agent | One still per call, about 8 per second at best on macOS |
| Rules | The user's business | Anti-cheat, and terms that ban automation | No game- or anti-cheat-aware policy |

### Mouse look needs deltas the server never sends

Microsoft documents three ways a Windows game reads the mouse: `WM_MOUSEMOVE`, which is limited to whole pixels and has pointer ballistics applied; Raw Input (`WM_INPUT`), read from the HID stack; and DirectInput, which reads `WM_INPUT` internally and is discouraged for mice ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/dxtecharts/taking-advantage-of-high-dpi-mouse-movement)). A first-person camera integrates Raw Input deltas while it hides, clips or recentres the cursor, the pattern SDL's relative mode packages for most engines ([SDL3 wiki](https://wiki.libsdl.org/SDL3/SDL_SetWindowRelativeMouseMode)). Raw Input flags each sample `MOUSE_MOVE_RELATIVE` or `MOUSE_MOVE_ABSOLUTE`, and Microsoft's own sample handles the two in separate branches ([RAWMOUSE](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawmouse)), so the server's `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK` moves (`native/src/mouse.rs:946-954`, `:1092-1096`) arrive as screen positions that a delta camera does not turn on. **Relative `MOUSEEVENTF_MOVE` is the right primitive, with two cautions.** On the legacy pointer path the mouse-speed thresholds can double a relative move twice, up to 4× ([MOUSEINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput)); Raw Input is documented as immune to the speed setting, but no source confirms that injected relative motion reaches `WM_INPUT` unscaled. And counts per degree belong to each game: Source-engine titles scale yaw by `m_yaw`, default 0.022 ([csdb.gg](https://csdb.gg/command/m-yaw/)), and Red Dead Redemption 2 smooths horizontal camera motion even with raw input on ([PCGamingWiki](https://community.pcgamingwiki.com/files/file/3936-red-dead-redemption-2-mouse-smoothing-fix/)). An agent has to calibrate a turn by injecting a known count and measuring the result, and should spread a large turn over time in small steps, as Lumine executes each relative command across its 200 ms step ([Lumine](https://arxiv.org/html/2511.08892)).

On macOS, SDL and Wine's mac driver (the base of CrossOver and Apple's Game Porting Toolkit) read `NSEvent` `deltaX/deltaY` in relative mode, not the event's position ([SDL source](https://raw.githubusercontent.com/libsdl-org/SDL/main/src/video/cocoa/SDL_cocoamouse.m), [Wine source](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/winemac.drv/cocoa_app.m)). The server's `mouse_move` posts `kCGEventMouseMoved` at an absolute point and never writes `kCGMouseEventDeltaX/Y` (`native/src/mouse.rs:529-545`); the only code touching those fields reads the person's deltas for takeover detection (`native/src/activity.rs:412-419`). Tools that do drive games set the delta fields before posting at the HID tap ([Keyboard Maestro forum](https://forum.keyboardmaestro.com/t/generate-low-level-mouse-movement-events/27923)); whether the window server would derive them from the position is undocumented, and a ten-line local experiment should settle it. **Even correct deltas will not reach every Mac game.** SDL 3 on macOS 14 and later takes relative motion from `GCMouse` whenever one is connected and then skips `NSEvent` deltas, and an SDL issue filed in September 2026 found that synthetic CGEvent clicks from remote-control and accessibility tools never reach SDL apps while a `GCMouse` exists ([SDL #16241](https://github.com/libsdl-org/SDL/issues/16241)). Only a virtual HID device is seen at the GameController level, and Apple's CoreHID virtual-device API sits behind an entitlement one developer had been waiting 2.5 months for ([Apple Developer Forums](https://developer.apple.com/forums/thread/845599)).

Linux has the narrowest gap but the most paths. On X11, `XTestFakeRelativeMotionEvent` shows up 1:1 as XI2 `RawMotion` (ten moves of +100 summed to exactly 1,000), while absolute XTest moves raise `RawMotion` carrying positions that a raw reader takes as large jumps ([roomler-ai #2380](https://github.com/gjovanov/roomler-ai/pull/2380)); the server's X11 `mouse_move` is `XWarpPointer` (`native/src/mouse.rs:28-60`), which produces no raw motion at all. On native Wayland a game holding a pointer lock receives only `wp_relative_pointer` motion ([pointer-constraints](https://isaacfreund.com/docs/wayland/pointer-constraints-unstable-v1)), and libei's relative `ei_device_pointer_motion` needs the pointer capability ([libei](https://libinput.pages.freedesktop.org/libei/api/group__libei-sender.html)). The server already binds `DeviceCapability::Pointer` on its libei seat but emits only `motion_absolute` (`native/src/linux_ei.rs:505-513`, `:598-607`), so relative motion there is a small change, provided GNOME and KDE advertise the capability to portal clients, which no source confirmed. XWayland adds a trap: after the master pointer copies the wrong slave device's valuator classes, Proton's mouselook reads raw deltas as absolute until the session restarts ([Proton #10189](https://github.com/ValveSoftware/Proton/issues/10189)). Mixing an absolute and a relative injected device could plausibly trigger it; running the game in nested gamescope sidesteps it ([gamescope](https://github.com/ValveSoftware/gamescope)).

### Keys need scan codes, real chords and hold time

Windows identifies a physical key by its scan code, which stays fixed across layouts while the virtual-key code can change; `KEYEVENTF_SCANCODE` tells `SendInput` to use it and `KEYEVENTF_EXTENDEDKEY` marks the `0xE0`-prefixed keys ([KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)). pydirectinput exists because PyAutoGUI's virtual-key approach fails in DirectX games ([pydirectinput](https://github.com/learncodebygaming/pydirectinput)). The server builds every Windows key event as `wVk: vk, wScan: 0`, with no scan-code or extended flag anywhere in the crate (`native/src/keyboard.rs:1062-1075`), and its key map has no numpad, Insert, Pause, Print Screen or right-hand modifiers (`native/src/keyboard.rs:969-1034`, `src/session/keys.ts:16-22`), so games bound to those keys cannot be driven. The exact mechanism by which raw-input games drop VK-only events is not confirmed from a primary source, which is why the plan below fills the scan code without removing the virtual key. A second defect hits games hardest: on macOS, Windows and X11 every non-modifier part of a combo overwrites a single `main_key`, so `key "w+a"` presses only `a` (`native/src/keyboard.rs:521-531`, `:1084-1098`, `:199-216`); only the libei path presses them all. Text is the wrong channel too, because `KEYEVENTF_UNICODE` arrives as `VK_PACKET` turned into `WM_CHAR`, not as a key a polling game sees ([KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)); the macOS `type mode: "keys"` route (`native/src/keyboard.rs:843-848`) exists for exactly that reason.

**A tap shorter than a frame can vanish.** A game that samples key state once per frame misses a down/up pair that falls between two samples, 16.7 ms apart at 60 fps and 33.3 ms at 30 fps. The Windows `key_press` sends the whole chord in one atomic `SendInput`, holding the key for 0 ms (`native/src/keyboard.rs:1078-1114`); clicks put button-down and button-up in one call (`native/src/mouse.rs:1108-1138`); macOS posts them back to back. Tools built for games hold deliberately: AutoHotkey's FAQ tells game users to set a 50 ms press duration or to send down and up with a sleep between ([AutoHotkey](https://www.autohotkey.com/docs/v2/FAQ.htm)), and VideoGameBench's `press_key` holds for 0.1 s by default ([VideoGameBench](https://arxiv.org/html/2505.18134)). Holding for at least two frames (35–50 ms at 60 fps, 70–100 ms at 30 fps) is a derived rule, not a measured one. Since 7.7, `hold_key` produces a real held state through a native key-down, an abortable timer and a key-up in `finally` (`src/session/input-handlers.ts:568-596`). But `key` and `click` take no duration, and the native `keyDown`/`keyUp` primitives (`src/native.ts:229-234`) are not exposed as tools, so a held W cannot overlap a mouse turn: `run_steps` awaits each step in turn (`src/session.ts:648-760`).

### Controllers, focus and window modes are walls, not gaps

`SendInput` synthesizes keystrokes, mouse motion and clicks and nothing else ([SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)), so a controller needs a virtual device, and every route in 2026 carries a cost a general npm package should not impose on its users. ViGEmBus, the de facto virtual Xbox 360 and DualShock 4 bus, was archived on 2 November 2023 and will get no further updates ([ViGEmBus](https://github.com/nefarius/ViGEmBus), [end-of-life notice](https://docs.nefarius.at/projects/ViGEm/End-of-Life/)). Microsoft's `InputInjector.InjectGamepadInput` needs the restricted `inputInjectionBrokered` capability, which means a packaged app ([Microsoft Learn](https://learn.microsoft.com/en-us/uwp/api/windows.ui.input.preview.injection.inputinjector)), and one open-source user calls it buggy ([VirtualGamePad-PC](https://github.com/kitswas/VirtualGamePad-PC)). The signed vJoy fork presents a DirectInput joystick rather than an XInput pad, and its author plans minimal maintenance ([vJoy](https://github.com/BrunnerInnovation/vJoy)). macOS has only the entitlement-gated CoreHID device. Linux is the one open path: Steam's own virtual controller is a uinput device with ID 28de:11ff ([SDL commit](https://cdn05042023.gitlink.org.cn/zinface/SDL/commit/c244eb937b7fb31202580f2a28f2e81e706f861e)), libei has no gamepad device ([libei #40](https://gitlab.freedesktop.org/libinput/libei/-/issues/40)), and write access to `/dev/uinput` is the same exposure `doctor` already flags for ydotool. The server has no controller support of any kind, and its person-protection has the mirror-image hole: the user-active guard and the takeover meter watch keyboard and mouse only (`native/src/activity.rs:365-445`, `:576-612`), so a person playing on a controller looks idle.

Focus is the other wall. `SendInput` has no window parameter and goes wherever focus is ([SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)); Raw Input reaches a background window only if the game registered `RIDEV_INPUTSINK` itself ([RAWINPUTDEVICE](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawinputdevice)); Unity pauses in the background unless `runInBackground` is set ([Unity](https://docs.unity3d.com/ScriptReference/Application-runInBackground.html)). The server's background route, `delivery: "pid"`, is macOS-only, and its own module warns that apps reading hardware state may ignore it (`src/session/pid-delivery.ts:1-14`). A game must therefore be foreground and stay there, and the agent must not activate its own UI between steps. Elevated games and launchers block injection from a non-elevated server, and Microsoft documents that neither the return value nor `GetLastError` identifies UIPI as the cause ([SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)), so the 7.7 `input_blocked` count check (`native/src/keyboard.rs:1043-1060`) should be backed by an integrity-level check before sending. Exclusive fullscreen hands the game the whole display, and an overlay over it must intercept rendering ([DirectX blog](https://devblogs.microsoft.com/directx/demystifying-full-screen-optimizations/)), so the status card, the person's visible Stop button, cannot be relied on there; the emergency chord, read by a low-level hook, should still work but has not been tested over a full-screen game. Borderless windowed is the agent-friendly mode for capture, focus and safety alike.

## A three-second decision spans 180 frames, so sample and synchronise rather than stream

The gap between a game's clock and an agent's is two orders of magnitude, and most of it is the model, not the server.

| Stage | Time | Source |
|---|---|---|
| One game frame at 60 / 30 fps | 16.7 / 33.3 ms | arithmetic |
| Persistent ScreenCaptureKit stream, steady state at 60 fps | 17.4 ms p50 per frame | [sckit-go](https://pkg.go.dev/github.com/LocalKinAI/sckit-go@v0.3.1) |
| This server's warm macOS window capture | 62 ms | `CHANGELOG.md:33-36` |
| This server's macOS `screenshot`, end to end | 112–128 ms | `CHANGELOG.md:33-36` |
| Accurate Vision OCR on 1–1.5 MP | 456–538 ms p50 | `docs/reviews/2026-10-23-competitor-study.md:110` |
| Cold focus before input | 160 ms of sleeps, plus up to 2 s of activation | `src/session/focus.ts:116-137` |
| Windows.Graphics.Capture first frame, new session per call | up to 1,500 ms | `native/src/capture_win.rs:361-470` |
| Lumine first action chunk (7B model on 4 GPUs) | 113.9 ms; 234 ms with reasoning | [Lumine](https://arxiv.org/html/2511.08892) |
| UI-TARS-2 interaction round | 4.0 s, cut to 2.5 s by W4A8 quantisation | [UI-TARS-2](https://arxiv.org/html/2509.02544v2) |

The arithmetic decides which games are in reach. A computer-use round of 2.5–4 s spans 150–240 frames at 60 fps. VideoGameBench's real-time mode, which hands the agent a frame half a second after each action, held Gemini 2.5 Pro and Claude 3.7 Sonnet to 0.48% completion, and no model passed 1.6% even when the emulator paused for thinking ([VideoGameBench](https://arxiv.org/html/2505.18134)); PokeAgent's real-time speedrun track found raw frontier VLMs at effectively 0% without a harness ([PokeAgent](https://arxiv.org/html/2603.15563)). **Aiming, platforming and racing are out of reach for any screenshot-model-action loop over MCP; turn-based, menu-driven and pausable games are not.** The server's job is not to reach 30 Hz. It is to let each call carry more time-precise motor content and to return observations synchronised with what the call just did.

Capture speed is not the bottleneck; freshness and timing are. Desktop Duplication keeps up with the display, with DXcam measuring a 239 fps average at 1080p on a 240 Hz output and hitting 30 and 60 fps targets within 2 fps ([DXcam](https://github.com/ra1nty/DXcam)), and a persistent ScreenCaptureKit stream costs 81 ms to open and then about 17 ms per frame, against roughly 89 ms for each one-shot window capture ([sckit-go](https://pkg.go.dev/github.com/LocalKinAI/sckit-go@v0.3.1)). The server takes one still per call: on macOS a `SCScreenshotManager` capture through a warm helper, serialised across servers (`src/session/macos-helper.ts:232-275`); on Windows a ladder whose Windows.Graphics.Capture rung builds a fresh session per call (`native/src/capture_win.rs:361-470`). The persistent stream the competitor study scheduled for 7.8 (`docs/reviews/2026-10-23-competitor-study.md:226`) is the right base for game observation as well.

Full-screen and HDR games are where Windows capture fails silently. Desktop Duplication returns `DXGI_ERROR_ACCESS_LOST` on mode changes and full-screen switches ([AcquireNextFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe)); Discord states that Windows.Graphics.Capture does not work for exclusive-fullscreen games and detects that mode to fall back ([Discord](https://support.discord.com/hc/en-us/articles/9410427556375--Windows-Capturing-Application-Window-for-Screen-Share-and-Go-Live)); HDR content captured without an FP16 pipeline and tone mapping comes out washed out ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)); and `PW_RENDERFULLCONTENT`, the ladder's first rung (`native/src/capture_win.rs:492-552`), is an undocumented flag adopted for DirectComposition apps, with no evidence it captures swap-chain games ([WebRTC commit](https://webrtc.googlesource.com/src/+/f89110d67902e787f6745ad2b52f7f09fc808512%5E%21)). The server treats an all-black frame as a failed rung (`native/src/capture_win.rs:286-295`) and rebuilds a lost duplication (`:55-211`), but it returns no named result telling the model it faces an exclusive-fullscreen game. OBS's faster game capture injects a hook into the game process, which anti-cheat products have detected ([OBS forum](https://obsproject.com/forum/threads/from-a-developers-perspective-what-does-anti-cheat-compatibility-hook-do.68483/latest)); the server must never do that. On Linux, nested gamescope gives one stable window and avoids the XWayland mouselook bug, while Steam Deck's embedded gamescope has no desktop to capture and exposes frames through its PipeWire node ([gamescope](https://github.com/ValveSoftware/gamescope)). On macOS, Game Mode switches on when a game enters full screen and lowers background-task priority ([Apple](https://support.apple.com/en-us/105118)); the server and its helper are background tasks then, and Apple documents nothing about the effect on capture.

The server's observation economy assumes still screens. Unchanged-frame deduplication compares exact hashes (`src/session/screenshot-handlers.ts:102-131`), so it almost never fires on an animated scene, and `wait_for_stable` calls a window stable only when consecutive capture hashes are identical (`src/session/agent-desktop-handlers.ts:326-352`), so it times out on a game unless the agent picks a static HUD region. VideoGameBench shows the alternative: it detects checkpoints by perceptual-hash matching at a Hamming distance under 12 ([VideoGameBench](https://arxiv.org/html/2505.18134)). Tolerance belongs in the waits. Deduplication should stay exact, because sending text in place of an image that changed slightly could hide the very change the agent needs to see.

Self-drawn interfaces close the last semantic channel. This repository measured Blender's macOS accessibility tree at six nodes (`AGENTS.md:520-562`), and its answer, OCR through `read_window_text` and `click_text`, is darwin-only in the catalog (`src/tool-catalog.ts:255-258`) and in the tool guide's game entry (`src/session/tool-guide.ts:144-152`). Yet the commercial-game agents in the literature drive Windows builds, Cradle through AutoHotkey and PyDirectInput ([Cradle](https://arxiv.org/html/2403.03186v3)). Engines have begun to publish trees: Godot 4.5 ships experimental AccessKit screen-reader support ([Godot](https://godotengine.org/releases/4.5/)), Unity 6.3 added native Narrator and VoiceOver support but its sample publishes the hierarchy only when a screen reader is detected ([Unity Discussions](https://discussions.unity.com/t/native-desktop-screen-reader-support-now-available-in-unity-6-3/1681788)), and Unreal exposes UMG widgets to Windows screen readers behind `Accessibility.Enable` ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/supporting-screen-readers-in-unreal-engine)). An automation client that is not a screen reader may still see nothing, which must be tested before the guidance changes. Text matters more than pixels for frontier models anyway: BALROG measured GPT-4o falling from 32.34% to 22.56% average progress when given images ([BALROG](https://arxiv.org/html/2411.13543v2)), Orak found image-only input caused a substantial drop ([Orak](https://arxiv.org/html/2506.03610v3)), and Gemini 2.5 Pro played Pokémon about as well without vision because its harness pulled screen text from RAM ([Drew Breunig](https://www.dbreunig.com/2025/06/17/an-agentic-case-study-playing-pok%C3%A9mon-with-gemini.html)).

## The agents that finish games freeze time, chunk actions or skip pixels

### Trained policies and frontier harnesses solve the clock differently

Two families exist. Frontier-model harnesses see a screenshot or short clip every few seconds and act through coarse primitives; trained vision-language-action policies run a small model at 5–30 Hz and emit relative deltas, key state per chunk, or gamepad vectors.

| System | Observes | Acts through | Handles the clock by | Reported result |
|---|---|---|---|---|
| Cradle, GPT-4o ([paper](https://arxiv.org/html/2403.03186v3)) | A 2 fps clip of the last action | Key press, hold and release; mouse move with speed; clicks | Pausing RDR2 and Stardew Valley | RDR2 tasks from 5/5 down to 1/5 |
| VideoGameBench agent ([paper](https://arxiv.org/html/2505.18134)) | Raw frames; five frames 0.1 s apart for DOS in Lite | Button presses, key holds with durations | Lite pauses the emulator | 0.48% full, 1.6% Lite at best |
| Pokémon harnesses ([TechCrunch](https://techcrunch.com/2025/05/03/googles-gemini-has-beaten-pokemon-blue-with-a-little-help), [LessWrong](https://www.lesswrong.com/posts/gogZyeistdaDFuhbG/claude-plays-pokemon-opus-4-5-follow-up)) | Screenshot plus RAM state, grid overlay or text minimap | Button sequences, navigator and pathfinder tools | Turn-based emulator | Gemini 2.5 Pro beat Blue; Opus 4.5 stuck at Victory Road near 230,000 steps |
| SIMA 2, Gemini Flash-Lite ([paper](https://arxiv.org/html/2512.04797v1)) | Stream of 720p frames | 96 keys, clicks, discretised relative mouse, in chunks | Real time, model chosen for latency | About double SIMA 1; 26 of 50 held-out MineDojo categories |
| Lumine, 7B ([paper](https://arxiv.org/html/2511.08892)) | 1280×720 at 5 Hz, 20-frame window | Relative ΔX/ΔY over 200 ms; six 33 ms key-state chunks | 114 ms to first action | Five-hour Genshin Impact storyline |
| Game-TARS ([paper](https://arxiv.org/html/2510.23691v1)) | Frames | `mouseMove(dx, dy)` capped at 180, click, keyPress at 50–100 ms | Time-paused web-game sandbox | 72.0 vs 42.1 for UI-TARS-1.5 on Minecraft embodied tasks |
| NitroGen, 500M ([paper](https://arxiv.org/html/2601.02427)) | One 256×256 frame | 16 buttons plus 4 stick axes, 16-action chunks | Intercepting the engine's system clock | Trained on 40,000 h across 1,000+ games |

The trained policies converge on one action vocabulary: relative mouse deltas, key state that persists across 33–100 ms chunks, and several actions per model call. The frontier harnesses converge on stopping the world: Cradle, VideoGameBench Lite, Game-TARS and NitroGen all pause or freeze the game while the model works. An OS-level server cannot intercept a commercial game's clock, but it can make "unpause, act for a fixed time, re-pause, capture" a single validated call. Real-time reasoning research points the same way at the harness level: AgileThinker, which runs a reactive thread beside a planning thread, kept a score of 0.58 at medium load and a 4k-token step budget, where planning-only reasoning fell to 0.05 ([Real-Time Reasoning Gym](https://arxiv.org/html/2511.04898v1)). That architecture is the host's to build; the server only has to make short, safe action chunks cheap.

**A caveat bounds the timeline idea.** Every model scored 0–10% on VideoGameBench's mouse-dragging practice game, and its authors found explicit hold durations confusing for models ([VideoGameBench](https://arxiv.org/html/2505.18134)). No source shows frontier models authoring millisecond timelines well without training, so the server should offer the timeline as a primitive for harnesses and skills, alongside coarse macros (hold for a duration, turn by a calibrated amount), rather than expect a model to choreograph 33 ms chunks.

### Harnesses move scores as much as models do

On lmgame-Bench, 40% of runs failed to beat a random player without the harness's perception and memory modules and 86.7% beat it with them ([lmgame-Bench](https://arxiv.org/html/2505.15146v2)). On UI-TARS-2's 15 browser games, normalised to human = 100, the purpose-trained UI-TARS-2 scored 59.77 against 24.73 for OpenAI's CUA and 21.61 for Claude Computer Use ([UI-TARS-2](https://arxiv.org/html/2509.02544v2)). The benchmarks built for frontier models (Orak, whose every game is an MCP server, and CivBench, with 76 MCP tools for Civilization VI) converge on exposed game tools and text state ([Orak](https://arxiv.org/html/2506.03610v3), [CivBench](https://arxiv.org/abs/2609.02459)), and PokeAgent found that generic CLI-agent harnesses lost coherence over thousands of decisions ([PokeAgent](https://arxiv.org/html/2603.15563)). **A server's observation and action affordances are part of the benchmark score, not neutral plumbing.** Cost confirms the direction: VideoGameBench ends runs at about $30 for roughly 2,000 steps ([VideoGameBench](https://arxiv.org/html/2505.18134)), so every turn a batch removes and every image the 7.7 dedup withholds is money.

### Engine servers now own the inside of the game

This is the route order the server's instructions already give, and the Blender skill already practises it, with the engine reporting where its panels are and computer-use acting on them (`skills/blender-agent/SKILL.md`). Because the engine endpoints are unauthenticated, the desktop server should detect and describe them on loopback, never start, configure or relay to them.

## Anti-cheat and publisher terms make refusal the safe default

Synthetic input is marked by design. A Windows low-level hook sees `LLMHF_INJECTED` and `LLKHF_INJECTED` on every injected event ([MSLLHOOKSTRUCT](https://learn.microsoft.com/windows/win32/api/winuser/ns-winuser-msllhookstruct)), and Raymond Chen confirms that `SendInput` input travels like hardware input yet remains detectable through that flag ([The Old New Thing](https://devblogs.microsoft.com/oldnewthing/20250319-00/?p=110979)). **The server's own safety model depends on the same markers:** its Windows guard drops injected events to tell the person from the agent (`native/src/activity.rs:576-612`), and on macOS it posts from a private event source for the same reason (`native/src/mouse.rs:519-523`). Disguising the agent's input would blind the takeover meter as surely as the anti-cheat. Kernel anti-cheat goes further: Riot says Vanguard "already outright rejects input from your non-primary peripheral device" ([Riot](https://playvalorant.com/en-us/news/dev/vanguard-hits-new-bans-per-second-record/)); EA's 2026 Javelin update lists blocks on malicious input devices, macro software and synthetic input tools ([EA](https://www.ea.com/news/ea-javelin-anticheat-2026-update)); a BattlEye "Disallowed Program" kick, commonly triggered by macro and automation tools, is not a ban ([Epic](https://www.epicgames.com/help/technical-support-c-36624475/c-Trending_0/disallowed-program-kick-battleye-a20061018)); Valve kicks CS2 players using Snap Tap-style input automation from official servers ([dust2.us](https://www.dust2.us/news/51933/cs2-8-19-update-null-binds-snaptap-and-jump-binds-banned-in-latest-update)). The first response to automation is usually a block or a kick, while bans follow behaviour, process tampering or publisher discretion, and false positives happen: VAC banned AMD Anti-Lag+ users in 2023 for detouring engine DLL functions before Valve reversed the bans ([PCWorld](https://www.pcworld.com/article/2106874/amd-anti-lag-is-causing-player-bans-in-counter-strike-2-apex-legends.html)), and Marvel Rivals banned macOS and Steam Deck players in January 2025 before NetEase reversed them ([GamingOnLinux](https://gamingonlinux.com/2025/01/marvel-rivals-team-issue-a-statement-on-recent-bans-for-steam-deck-and-macos-players)). Two things remain unknown: no vendor documents how Easy Anti-Cheat or BattlEye treat `SendInput`, and no report was found of an account banned for letting a general AI computer-use agent play, an absence that may reflect low usage rather than tolerance.

Capture is safer but not policy-neutral. No source shows an anti-cheat flagging compositor capture or OCR as such; hook-based capture is what gets blocked, and screen-reading cheats are caught by what they do with the mouse. Riot's developer policy, however, bars apps that improve a player's performance in real time by telling them where to go or what the opponent will do ([Riot Developer API Policy](https://support-developer.riotgames.com/hc/en-us/articles/22698732381587)), so a watching coach can break a title's rules without touching input, and Microsoft's Gaming Copilot drew scrutiny when a user saw it sending captures from a game under NDA ([Tom's Guide](https://www.tomsguide.com/ai/copilot/gaming-copilot-ai-under-fire-but-microsoft-says-its-not-training-ai-models-on-your-data)).

The terms leave little room. The Steam Subscriber Agreement has a separate Automation section barring scripts, bots, macros and other non-human-controlled systems, and a separate clause forbidding interference with anti-cheat software ([Steam](https://store.steampowered.com/subscriber_agreement/)); read through a summarising fetch, the Automation section showed no single-player or accessibility exception and covered earning progress without genuine user input, wording to verify verbatim before publishing. Riot's terms ban unauthorised automation programs that interact with its services in any way and for any purpose ([Riot](https://www.riotgames.com/en/terms-of-service)), Blizzard's EULA bans unauthorised code that allows automated control of a game ([Blizzard](https://www.blizzard.com/en-us/legal/fba4d00f-c7e4-4883-b8b9-1b4500a402ea/blizzard-end-user-license-agreement)), and Epic's Fortnite EULA ties its prohibition to advantage over other players ([Epic](https://cdn1.epicgames.com/eulatracking-download/fn/en/v9/r8/3b853b765f5c4f9129b31e349d0775c5.pdf)). No publisher found has an AI-agent policy or a formal accessibility exemption; EA points players who need remapping to Steam Input or Microsoft's Keyboard Manager instead ([EA Forums](https://forums.ea.com/discussions/ea-forums-general-discussion-en/ea-javelin-anticheat--recent-software-blocks/12218073)). Single-player is therefore not safe ground on Steam: an agent that unlocks achievements carries account-level risk that has nothing to do with anti-cheat.

AI vendors have set the pattern without naming games. Anthropic's usage policy prohibits using its models to circumvent other platforms' terms or to bypass monitoring tools without authorisation ([Anthropic AUP](https://www.anthropic.com/legal/aup)); Claude Code assigns apps control tiers and blocks sensitive categories by default ([Claude Code](https://code.claude.com/docs/en/computer-use), [Help Center](https://support.claude.com/en/articles/14128542-computer-use-safety)); Gemini's sample instructions forbid solving CAPTCHAs or any other anti-robot mechanism ([Gemini API](https://ai.google.dev/gemini-api/docs/computer-use)); Operator hands CAPTCHAs to the user ([OpenAI](https://openai.com/index/introducing-operator/)). The publicly sanctioned ceiling for AI in commercial games is Microsoft's Gaming Copilot, an advisor that watches rather than plays ([Xbox Wire](https://news.xbox.com/en-us/2025/08/06/gaming-copilot-beta-begins-rolling-out-to-xbox-insiders-on-game-bar-today/)). No general-purpose automation product was found that detects anti-cheat and refuses, so this server would set the pattern.

The defaults follow. The server should detect protected games and refuse input to them by default with a named reason; keep capture and OCR available with a warning about live-advice rules and confidential builds; allow automation only per title, through an operator setting, never through `force` or anything the model reads on screen; never hide, disguise or "humanise" synthetic input; hand human-verification challenges to the person; and document the intended uses. Those are games the user develops, engine editors, open-source games, emulators running ROMs the user dumped (the server must never fetch ROMs), and offline single-player copies with the residual terms risk stated. Online, ranked and account-progress play on Steam, Riot, Blizzard or Epic titles is out. Detection by process name is defense in depth, like the existing `run_script` body matching, and anti-cheat names change between versions, so the list must be compiled from vendor documentation and stay operator-extensible.

## A four-tier plan for computer-use-mcp

The plan serves three audiences in order: developers testing their own builds, whom engine routing and real input fidelity serve; offline, single-player and emulated play, including research harnesses, which need relative input, timelines and synchronised observation; and online competitive play, which the server refuses. P0 is restraint and truth, changes that stop the server doing harm or reporting input that never landed; P1 adds reach; P2 adds observation and Windows parity; P3 is spikes. Each item reuses an existing seam, as the competitor study's plan did: the policy list, the dispatch gate, the refusal contract, `run_steps`, the held-key latch and the persistent helper. Every new input primitive keeps five invariants. It passes the same dispatch gates as `click`: the policy check (now including the protected-game gate), the session-state refusals (`src/session.ts:270-290`), the user-active guard and the person's Pause and Stop. It is released by the native latch, which already tracks held keys (`native/src/keyboard.rs:860-944`) and all three buttons (`native/src/mouse.rs:515-517`). It is bounded in magnitude and duration, since relative moves have no display bounds to check. It reports `effect` honestly: a relative move or a game key cannot be verified geometrically, so it is `unverified` unless `verify: true` captures before and after. And it never takes the pid route to a game. Item 12 carries a caveat: an Apple engineer said in 2021 that `GCMouse` and `GCKeyboard` deliver events only to the foreground app ([Apple Developer Forums](https://developer.apple.com/forums/thread/696020)), and no source says whether a background process can observe a controller through GameController, so background controller detection on macOS must be proven before it is promised.

Verification needs fixtures, not commercial games. Testing against an anti-cheat title would itself breach the terms the plan respects, so each claim should be checked with small self-built or open-source programs: a Win32 Raw Input logger that prints `usFlags`, `lLastX/lLastY` and `MakeCode`; an SDL 3 relative-mode sample on all three platforms, run with and without a physical mouse to expose the `GCMouse` path; a frame-polling key fixture at 30 and 60 fps; and a DX11 sample that can run windowed, borderless and exclusive with HDR on and off. Raw Input and scan-code tests fit the Windows CI runner. Exclusive fullscreen, HDR and multi-monitor behaviour need the hardware check the competitor study already requires of the #40 contributor, and the Wayland relative pointer needs a GNOME and a KDE run, because no source confirms either compositor advertises the capability to portal clients.

Several things should never be built, and saying so in AGENTS.md closes them for good. Kernel or virtual-HID injection drivers make input look like hardware, which is exactly what anti-cheat polices; Interception, the usual example, needs an administrator install ([Interception](https://github.com/oblitum/Interception)), stopped Valorant launching under Vanguard in 2020 ([Ginx](https://www.ginx.tv/en/valorant-vanguard-hotfix-mouse-keyboard-input-device-driver)) and is flagged by Javelin by driver name ([EA Forums](https://forums.ea.com/discussions/fc-26-technical-issues-en/ea-javelin-anticheat-falsely-detects-interception-on-windows-11-steam-version/13540404)). Clearing injection markers or "humanising" timing to slip past detectors would turn a terms breach into deliberate circumvention. Hook-based capture modifies the game process. Reading game memory is what Riot began blocking for unknown apps on 6 October 2026 ([Riot Support](https://support.riotgames.com/ar-ae/riot/performance/game-memory-access-removed-for-third-party-apps)). Silently changing the person's mouse-acceleration settings, as pydirectinput_rgx does for the duration of a move ([pydirectinput_rgx](https://github.com/ReggX/pydirectinput_rgx)), would alter a user-visible setting without consent. Solving CAPTCHAs or anti-cheat challenges is ruled out for the reasons above. Process suspension as a default pause is unmeasured on commercial games and indistinguishable from tampering to a watchdog.

The tiers map onto releases. P0 is mostly TypeScript plus one native keyboard change and fits a 7.7.x patch. P1 belongs in 7.8 beside the persistent helper and stream the competitor study already scheduled, and the `game` profile pays for its new schema bytes without eating into the `desktop` budget, which stood at 44,324 of 48,000 bytes (`AGENTS.md`). P2 is Windows-heavy and gated on hardware. P3 stays a spike. For the Unreal Editor itself, the v8 app-bridges plan (`docs/specs/v8-app-bridges/requirements.md`) remains the long-term route for background, cursor-free input; OS-level relative input is for standalone builds, PIE sessions where the real input path is under test, and games with no bridge at all.

## Conclusion

The research turns "should the agent hide its input?" from an ethical question into an engineering one. The injected-input flags and private event source that anti-cheat reads are the same markers this server uses to tell a person from the agent, so concealment would disable takeover and the user-active guard along with any detector it fooled; honest synthetic input is the only design in which the person's controls keep working. The same evidence reorders the value of features. Frontier models gain most when time stops and text replaces pixels (a harness cut lmgame-Bench's share of runs no better than random from 40% to 13.3%), while pixel-only real-time play stays under 2% whatever the input fidelity. Relative motion, scan codes and timelines are therefore necessary for reach rather than sufficient for skill, and the server's most valuable game features are the ones that make a pause-act-capture cycle one honest call and that route the agent to engine or emulator state wherever it exists.

The gap list is also mostly a Windows list (scan codes, exclusive fullscreen, HDR, elevation, OCR, capture sessions) on the platform where this repository has the least hardware coverage, and nearly every claim about which injected events reach which games is unverified title by title. That puts the burden on the result contract 7.7 just shipped. In games, `effect: "unverified"` will be the common answer, and an agent told the truth about that will waste fewer turns than one told "pressed" for a key the game never saw. Two fixes surfaced here are worth shipping whatever the gaming roadmap becomes: the multi-key combo that presses only its last key is a defect for any caller, and filling the Windows scan code beside the virtual key is harmless to ordinary apps while it gives raw-input readers the physical key they expect.
