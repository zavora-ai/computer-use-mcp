## 0. Headlines (the things most worth knowing)

## 2. macOS specifics

**Window pick.** Two parallel implementations. (a) Native `main_window_for_pid` (screenshot.rs:351-395): layer-0, alpha>0, owner pid from `pid_for_bundle` (NSWorkspace.runningApplications, :291), score (has title, area), ties to frontmost. (b) TS `selectMainWindow` / `resolveAppWindow` (src/session/window-select.ts:66-85, 238-262), which the v7.5 screenshot path uses and then hands native a `window_id`; the native one remains only as fallback. `target_title` is a substring filter in TS only. Titles need Screen Recording; without it all titles are empty and area decides (comment at screenshot.rs:346-350). list_windows is on-screen-only, so minimised or other-Space windows are invisible to `resolveAppWindow`.

**Coordinates.** All input is global CG display coordinates in points, origin top-left of the primary display (secondary displays can be negative). Retina is handled by never using pixels for input: window screenshots print `screen_x = frame.x + image_x * scale` (screenshot-handlers.ts `#sckScreenshot`, exact because SCK omits the shadow); the non-SCK window path prints an approximate mapping because the shadow adds pixels (`#describeCapture`, :205-235); whole-screen capture maps with `getDisplaySize()` of the **main** display only (`display.width / image.width`), so a full-screen capture mapping is wrong for any window on a second display, and `screencapture` has no `-D` here (display selection is not wired; behaviour of plain `screencapture -x` with 2 displays not verified). The Swift helper computes `scale = image.width / rect.width` from `SCContentFilter.pointPixelScale` (swift:77-99) and forces 2x for OCR on 1x displays (`minPixelScale`).

**Pid delivery.** `CGEvent::post_to_pid` (keyboard.rs:300, mouse.rs:744-788), events built from a Private-state `CGEventSource` (keyboard.rs:285, mouse.rs:443). Mouse events are tagged with kCGMouseEventWindowUnderMousePointer (91) and ...ThatCanHandleThisEvent (92) = target window id so Cocoa routes to the right window even when covered (mouse.rs:710-720). TS wraps it with capture-before/after verification and a per-app, per-class (keyboard / pointer) record in `~/Library/Caches/computer-use-mcp/pid-delivery.json` (src/session/pid-delivery.ts); `delivery: "auto"` uses pid only for apps recorded `changed`. Measured (design §6, release notes): keys reach a background TextEdit and Unreal (`stat fps` in the Unreal log); menu shortcuts (cmd+p) and clicks do not (inactive window drops the first click; key equivalents go through the active app's menu). Blender spike still pending. No dedicated shortcut route exists, so "games bind keys not characters" is handled by `type mode:"keys"` (keyboard.rs:748, key down/up from the live layout, Unicode fallback for characters the layout lacks).

**User-active guard.** Measures time since the last event whose `kCGEventSourceStateID == 1` (hardware HID) seen by a passive `ListenOnly` HID tap on its own thread (activity.rs:276-391). Synthetic events use a Private source (-1), so the server's own input is excluded. Threshold `COMPUTER_USE_USER_IDLE_MS`, default 4000 on macOS, 0 (off) on Windows/Linux unless set (src/session/user-activity.ts:~65). Problems: (1) the first-call bug in section 0; (2) if the tap cannot install (no Input Monitoring) it returns `None` and the guard allows everything, only `doctor` says so (user-activity.ts header comment); (3) tap install blocks the napi thread up to 2 s (`recv_timeout`, activity.rs:379).

**TCC.** What exists today (#35): `AXIsProcessTrusted` / `CGPreflightScreenCaptureAccess` exposed host-only (permissions.rs:46-60); `doctor` checks 'display_capture' by taking a screenshot and 'accessibility' by listing the frontmost app (src/session/doctor.ts:68-135), which pass even when untrusted (CGEventPost from an untrusted process is silently dropped; listing windows works without AX). Input Monitoring is only discovered when the tap fails to install ("Input Monitoring permission may be missing", activity.rs:354). Screen capture failures surface as the bare string "screencapture failed" (screenshot.rs:430). The SCK helper maps denial to `screen_recording_denied` (swift:66-70). PR #34 fixes the first two: `ensure_input_trusted()` on all HID input (permissions.rs), `capture_failure_reason` naming Screen Recording, `.output()` instead of `.status()` so the child cannot write to the MCP stdout, doctor accessibility check via real trust, and an overlay fix using the primary screen height (`NSScreen.screens[0]`, not `mainScreen`) for multi-display. #34 does not guard the new `*_to_pid` functions (those post via `post_to_pid`, which also needs trust).

**Known limits (documented, matches observed).** Menu shortcuts and clicks do not reach background apps; games read keys, not characters; Swift helper needs `swiftc` (Xcode CLT) on first use: without it no SCK window capture (falls back to screencapture) and no OCR (no fallback).

## 3. Build and ship

- **Native addon**: Rust cdylib, `napi` 2 with `napi9` feature (native/Cargo.toml:17). N-API is ABI-stable, so there is **no per-Node-version prebuild matrix**; one binary per OS/arch loads on every Node >= 18.17/20.3. Verified: `computer-use-napi.node` loads on Node v25.4.0 (napi v10), 65 exports including the v7.5 pid/keys/guard functions.
- **Where it lands**: repo root, gitignored (`*.node`). `npm run build:native` (package.json) builds, copies `libcomputer_use_napi.dylib` to both `computer-use-napi.darwin-<arch>.node` and the generic `computer-use-napi.node`, ad hoc codesigns. Windows/Linux have separate scripts; `build:native:win` uses `copy` (cmd only). Local binaries here are arm64-only, built 2026-10-01 09:39; load path embedded in LC_ID_DYLIB is the absolute build path (harmless).
- **What npm users get**: the **universal tarball contains all six binaries** (package.json `files` lists them) built in CI `build-native` and re-packed in the `publish` job (ci.yml, "Verify universal tarball contains every native target"). npm users do not compile. Unpacked size 10.4 MB (npm view). The `optionalDependencies` list contains only playwright; the six platform packages are not referenced and not published (all 404).
- **Resolver** (src/native.ts:48-97): `COMPUTER_USE_NATIVE_PATH` > optional platform package > root `computer-use-napi.<platform>-<arch>.node` > root generic `.node`. Unsupported platform/arch throws a clear error; a missing binary throws a doctor-friendly error (but advises the unpublished packages). `loadNative()` is lazy (`require` on first use), which is why CI's install matrix (which only imports entry points) never loads the addon on Node 22/24/current.
- **Node version with no prebuild**: not a concept here (N-API). A Node < 18/20 fails on engines (`>=20`). Dependencies `@modelcontextprotocol/*` 2.0.0 declare `>=20`; zod 4.3.6.
- **dist/**: `npm run build:ts` = `node scripts/clean-dist.mjs && tsc` (tsconfig.json), gitignored, `prepublishOnly` runs full `build` (native + ts) so a local `npm publish` would pack whatever binaries sit in the root (could be arm64-only); CI is the intended path.
- **macOS helper**: not prebuilt; Swift source in `libexec/` compiled at runtime into `~/Library/Caches/computer-use-mcp/macos-agent-helper-<sha8>` (src/session/macos-helper.ts:124-152; 180 s compile timeout, 10 min retry back-off).
- **Node 25.4 start-up risk**: none found. Native loads (checked). `engines >=20`. CI never runs the full suite or loads the addon on Node 24/25 (test job is Node 20 only; install matrix imports only). `@types/node ^22` and `engines` make Node 25-only type/API drift untested. Stale artifact to know about: packages/computer-use-mcp-darwin-arm64/computer-use-napi.darwin-arm64.node is dated Jul 10 and lacks pid delivery (untracked); `npm pack` there would ship an old addon unless `prepare:packages` ran.

## 6. Known issues: where they live and what a fix takes

**#32 agent_pointer overlay deadlock, Windows 11 (open).** native/src/overlay.rs:273-541 (`win` module). Cause was synchronous cross-thread `SetWindowPos`/`ShowWindow` against the overlay thread's window. v7.4.0 fix (cfbb6af, in main): state recorded under a mutex, applied via posted `WM_APPLY_OVERLAY`; `READY` flag set only when the pump runs; `GetMessageW` -1 handled. Maintainer comment says it is **not verified on Windows**; issue left open. Residual: `hwnd()` (overlay.rs ~:446) still polls up to 750 ms on the napi (event loop) thread with `sleep(10ms)` on first use; `agent_pointer_overlay_hide` calls `hwnd()` (so it can start the thread just to hide); no DPI awareness set anywhere (mixed-DPI placement, reporter's setup, is unverified). Fix to close: S to make `hwnd()` non-blocking (start thread, return not-ready), M to verify on a real Windows 11 mixed-DPI box (needs a tester; the reporter offered).

**#21 empty AXWindow nodes on Linux (open, reported on 7.1.0).** At 7.1.0 `get_ui_tree` was the stub at native/src/accessibility.rs:3-60. v7.2 (5a62b06) added src/session/linux-atspi.ts + libexec/linux-atspi.py, a Python bridge that returns real children (limit 500 nodes, depth <= 30). The reporter also saw `list_windows` empty: consistent with `wmctrl` missing (windows.rs:67-70 silently substitutes `true`), which then makes `getWindow` return nothing and the bridge `window_unavailable`. Remaining weaknesses in the bridge: window match requires `get_name() == title` exactly, with pid from wmctrl (Qt/GTK3 apps, empty titles, or Xfce title decorations mismatch -> "inaccessible or ambiguous"); roles map covers ~12 names; `value` is always null; Qt apps need `QT_ACCESSIBILITY=1`. Not retested after 7.2; comment/close candidate once someone confirms on Xfce. Fix: S (surface "install wmctrl/xdotool" instead of an empty list; add the tools to workers/linux/Dockerfile); M (replace wmctrl/xdotool with native X11 `_NET_CLIENT_LIST` + `XGetWindowAttributes` so bounds are real and no shell-outs remain).

**#36 per-platform packages (open, 2026-10-08, no maintainer reply).** Asks: planned? blocker? community PR welcome? is `COMPUTER_USE_NATIVE_PATH` a stable contract? Facts: manifests exist (packages/computer-use-mcp-<os>-<arch>/package.json with `os`/`cpu`, `files`), versions stamped by scripts/prepare-platform-packages.mjs, resolver step 2 implemented and tested (test/platform-packages.test.mjs), CI deliberately refuses to publish a root manifest that references them (ci.yml "must not reference unbootstrapped optional packages"). Missing: a publish job (6 `npm publish` with provenance from the already-built artifacts), first-publish bootstrapping on npm (scope `@zavora-ai` new package names need creating and trusted-publisher OIDC set up per package), `optionalDependencies` pinned to the exact version in the root manifest (after the packages exist), fixing the error text, deciding whether to keep binaries in the root tarball too (bundlers like the reporter's esbuild want them out).
