# Share the screen by gating, not streaming

computer-use-mcp can give Claude a "share your screen" experience, but only as an event-driven session run by a host the project controls. It cannot work as a Gemini-Live-style frame stream, and stock MCP hosts cannot carry one. Claude has no realtime, bidirectional or audio API. Every frame is a complete Messages request, and output streams back over SSE. Measured time to first token runs from 1.40 s (Sonnet 5.5 at low effort) through 4.90 s (Opus 5.5, which cannot turn thinking off) to 6.68–7.62 s (Haiku 5.5 with thinking on). A 1 fps feed would therefore keep three to eight answers in flight, each about a screen that has already changed, and it would cost $0.95 an hour on Haiku 5.5, $34–56 on Opus 5.5 and $69–112 in Opus fast mode. The hosts cannot carry the stream either. No core MCP notification carries an image. Claude Desktop and claude.ai support neither resource subscriptions nor sampling. Claude Code channels inject only text, and only on the legacy handshake. MCP Apps can show a person a live view by polling, but they reach the model only when a turn starts. The better design keeps the stream local. A persistent capture source in the server feeds two consumers: a person-facing view at 1–2 fps, and a layered change gate built on OS idle and dirty-rect signals, downscaled hashes, window events and OCR text deltas. The model receives a crop, a frame or a text delta only when the gate fires or the person speaks. Haiku 5.5 triages each event with thinking off and no tools, and Opus 5.5 handles the events Haiku escalates. At 60–720 gated events an hour, that tiered loop costs about $0.14–1.65 ($0.26–3.14 with Opus fast mode). Its reaction time of 3–8 s is no worse than raw streaming's, because the model, not capture, sets the floor. Fast mode buys output speed, not reaction time: it leaves first-token latency unchanged, saves about 1 s on a 150-token reply and saves about 11 s on a 1,500-token action plan. Most server-side pieces already exist. Five are missing: a persistent capture stream, an event source that runs between tool calls, a visible "watching" state, accessibility event observers and a host driver loop.

## Claude has no session to stream into, and hosts cannot push into the model

Anthropic documents only text and images in, text out, for every current model ([Models overview](https://platform.claude.com/docs/en/about-claude/models/overview.md)). Streaming means server-sent events for output, with no WebSocket and no way to stream input ([Streaming](https://platform.claude.com/docs/en/build-with-claude/streaming.md)). An image arrives as base64, a URL or a Files API id; there is no stream or video source type ([Vision](https://platform.claude.com/docs/en/build-with-claude/vision.md)) **[doc]**. Two consequences follow. **A live Claude loop is a client loop of repeated, complete requests.** A frame or a typed sentence that arrives while the model is answering waits for the next request. To react to a change mid-answer, the client cancels the stream and starts again; nothing documents whether output generated before the cancel is billed. Voice exists only in the consumer apps, as a beta with hands-free turn-taking. The help centre says that "in Claude Cowork and Claude Code, dictation is available but voice mode isn't" and mentions neither screen sharing nor the API ([Using voice mode](https://support.claude.com/en/articles/11101966-using-voice-mode)) **[doc]**. That contradicts a March 2026 report of a Claude Code "voice mode" rollout ([TechCrunch](https://techcrunch.com/2026/03/03/claude-code-rolls-out-a-voice-mode-capability/)) **[3P, search summary only]**. This review follows the help centre. The screen features Anthropic ships are screenshot-per-action. Claude Code desktop's computer use is a macOS and Windows research preview that its own docs call "the broadest and slowest" route ([Claude Code desktop](https://code.claude.com/docs/en/desktop)). That is the same pattern as this server.

The settings that control latency differ by model, and they matter more than raw speed. Haiku 5.5 accepts `thinking: {type: "disabled"}` at effort `high` or below. Sonnet 5.5's lowest setting is `between_tools`. **Opus 5.5 cannot turn thinking off**, and changing thinking or effort between requests starts a new cache prefix ([Thinking](https://platform.claude.com/docs/en/build-with-claude/thinking.md)) **[doc]**. Opus 5.5 fast mode is GA with no beta header, priced at $8 input and $40 output per million tokens. Anthropic's fast-mode page says its gains are "focused on output tokens per second (OTPS), not time to first token (TTFT)" and that "requests at different speeds do not share cached prefixes" ([Fast mode](https://platform.claude.com/docs/en/build-with-claude/fast-mode.md)) **[doc]**. Anthropic publishes only relative latency labels. Artificial Analysis supplies the numbers, measured on its own text prompts rather than image prompts:

Haiku's TTFT almost certainly reflects up-front thinking, not slow prefill, since its output speed is the highest in the lineup. Older snapshots disagree with these figures: one review gives 14.2 s and another 13.40 s for Haiku at medium effort ([eesel](https://www.eesel.ai/blog/claude-haiku-5-5-review), [Kingy.ai](https://kingy.ai/blog/claude-haiku-5-5-benchmarks-specs-sol-luna/)) **[3P]**. This review uses the current AA snapshot. The configuration that matters most for a live triage tier, Haiku with thinking disabled, has never been measured.

Vision cost is now exact. An image costs `⌈width/28⌉ × ⌈height/28⌉` visual tokens: 1,334 for a 1280×800 frame, 784 for the 768×768 frame Google recommends for Live, and 100 for a 280×280 crop. The 5.5 models sit on a high-resolution tier capped at 2,576 px and 4,784 tokens. There is no "low detail" switch, so pixel count is the only cost control ([Vision](https://platform.claude.com/docs/en/build-with-claude/vision.md)) **[doc; token counts computed]**. Caching is an exact prefix match, not deduplication. Adding or removing an image anywhere in the prompt invalidates the messages cache from that point. Cache reads cost 0.1x on Haiku 5.5 and 0.05x on Opus 5.5 ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching.md)) **[doc]**. Haiku's $0.10 rate also has a cliff. **A Haiku 5.5 request whose prompt passes 100,000 tokens, cache reads included, pays 5x on every token** ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing.md)) **[doc]**. A history that keeps every 1280×800 frame crosses that line at turn 62 **[computed]**. On the 5.5 models Anthropic advises against pruning old screenshots on the client, because that invalidates later thinking blocks; it recommends server-side tool-result clearing instead ([Computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool.md)) **[doc]**.

The MCP side closes the remaining routes. In the 2026-07-28 revision, `notifications/progress` carries a text message, `notifications/resources/updated` carries only a URI, and logging is deprecated. **No core notification carries an image.** A screen reaches a model only as a tool result, a resource the client chooses to read, a deprecated sampling request, or through an MCP App ([2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [Subscriptions](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions), [Deprecated features](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)) **[doc]**. The tasks extension returns its result once, at completion, and forbids progress notifications on tasks ([SEP-2663](https://modelcontextprotocol.io/seps/2663-tasks-extension)) **[doc]**. Partial tool results (SEP-2998) were closed on 2026-09-22 ([PR #2998](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2998)). The proposals that would help remain open and unshipped: server events that re-enter the model (SEP-2495), an events extension (SEP-3415) and binary resource streaming for HTTP only (SEP-2532). No SEP or working group covers realtime media ([PR #2495](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2495), [PR #3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415), [PR #2532](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2532)) **[doc]**. Two conclusions follow, both **[doc]**. First, **MCP Apps is the only rich channel that reaches most hosts**, and its spec offers only one live pattern: the view polls tools. The official system-monitor example polls an app-only tool every 2 s ([MCP Apps draft spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/draft/apps.mdx), [system-monitor example](https://github.com/modelcontextprotocol/ext-apps/tree/main/examples/system-monitor-server)). The sandbox can grant camera and microphone but not screen capture, so pixels must come from the server. Second, **only a host that runs its own model loop can let a screen change start a turn.** Every stock host either batches pushed events until the next turn or asks the person before starting one.

## A raw 1 fps feed keeps three to eight answers in flight

The cost model applies one set of assumptions to every design. Each call carries a 5,000-token cached prefix (system prompt and tools), 50 uncached text tokens and 150 output tokens, at October 2026 list prices ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing.md)). Opus 5.5 cannot turn thinking off, so its calls in D3–D5 carry an *assumed* 300 thinking tokens, billed as output; no source gives a per-call figure. D1 and D1′ are shown without thinking, so their Opus figures are a floor. "Gated events" are the times the change gate or the person wakes a model: 60 an hour (quiet), 240 (moderate) or 720 (busy, one every 5 s). The tiered design escalates an *assumed* 10% of events to Opus, sending the frame plus 600 tokens of recent captions and asking for 300 output tokens. The local-perception design sends a 200-token text delta and attaches a frame on an *assumed* 20% of calls. The research note's own 1 fps figures leave out the 50 text tokens: it gives $0.93 an hour for Haiku against $0.95 here. All figures are **[computed]**.

| Design | What the model receives | Haiku 5.5 $/h | Opus 5.5 $/h | Opus 5.5 fast $/h |
|---|---|---|---|---|
| D1 Raw stream, 1 fps, 1280×800, stateless | Every frame | 0.95 | 34.33 (55.93 with thinking) | 68.66 (111.86) |
| D1′ Gemini-style sampler, 0.5 fps, 768×768 | Every other second | 0.38 | 13.20 | 26.41 |
| D3 Gated full frames (60 / 240 / 720 events per hour) | One frame per event | 0.02 / 0.06 / 0.19 | 0.93 / 3.73 / 11.19 | 1.86 / 7.46 / 22.37 |
| D3b Gated crops (400-token mean) | The changed region | 0.01 / 0.04 / 0.12 | 0.71 / 2.83 / 8.50 | 1.42 / 5.66 / 16.99 |
| D4 Tiered: Haiku triages every event, Opus takes 10% | Haiku: the frame. Opus: the frame plus captions | (included) | **0.14 / 0.55 / 1.65 total** | **0.26 / 1.05 / 3.14 total** |
| D5 Local text deltas, frame on 20% of calls | 200-token delta | 0.01 / 0.04 / 0.12 | 0.71 / 2.85 / 8.54 | 1.42 / 5.70 / 17.09 |
| Gemini 3.8 Live, 1 fps, open microphone, model speaks 6 min | Every frame plus audio | $0.63–1.31 if each token is billed once; $1.7–34 if full context is billed per turn | | |

The latency picture explains why D1 fails on more than cost. The floor for "something appears, the first useful words come back" is the sum of capture, debounce, time to first token and output:

| Stage | Time | Source |
|---|---|---|
| Warm macOS helper capture; `screenshot` end to end | 62 ms; 112–128 ms | `CHANGELOG.md:45-46` **[inventory]** |
| Persistent ScreenCaptureKit stream: open, then per frame at 60 fps | 81 ms, then about 17 ms | [sckit-go](https://pkg.go.dev/github.com/LocalKinAI/sckit-go@v0.3.1) **[3P, not measured on this codebase]** |
| Change-gate debounce | 200–500 ms | screenpipe performance and balanced profiles ([profile.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-engine/src/power/profile.rs)) |
| Accurate Vision OCR on 1–1.5 MP | 456–538 ms p50 | `docs/reviews/2026-10-23-competitor-study.md:110` **[inventory]** |
| Whole loop, 150-token reply: Sonnet 5.5 low | 3.1–3.5 s | **[computed]** from AA |
| Whole loop: Opus 5.5 fast / Opus 5.5 low / Haiku 5.5 with thinking | 5.9–6.3 s / 7.0–7.4 s / 7.8–8.2 s | **[computed]** from AA |

At one frame a second, those service times keep about 2.8 Sonnet, 6.7 Opus or 7.5 Haiku requests in flight. Each answer describes a frame several seconds stale, and the client has to discard or reconcile overlapping replies. **Raw streaming is affordable on Haiku but pointless, and expensive as well as pointless on Opus.** Gating makes the loop slower in no way that matters: the 0.2–0.5 s debounce is a tenth of the model's time to first token. Capture is not the bottleneck either. OSWorld-Human attributes 75–94% of agent task time to planning and reflection, and only 1–4% each to screenshot capture and action execution ([OSWorld-Human](https://arxiv.org/html/2506.16042v1)) **[3P]**.

**On Opus, the number of calls is the only cost lever that matters.** In an Opus 5.5 call with a 1280×800 frame and 300 thinking tokens, the cached prefix is 6% of the cost, the frame and text 36%, and output plus thinking 58% **[computed]**. Shrinking pixels therefore saves at most about a third: crops take the busy hour from $11.19 to $8.50, and text deltas save no more. Removing calls saves in proportion, so triaging with Haiku takes the same busy hour to $1.65, 85% less. Against a 1 fps Opus stream with thinking, tiering is 97% cheaper. It also changes how far a Start-tier organisation's $500 monthly cap stretches, from about 15 hours of raw Opus streaming to about 300 busy hours of the tiered loop **[computed; cap from [Rate limits](https://platform.claude.com/docs/en/api/rate-limits.md)]**. Haiku inverts the picture: triage costs $0.01–0.16 an hour, cheap enough to send it full frames whenever the gate fires and reserve text deltas for latency and privacy.

**Fast mode pays only when Opus writes a lot.** Time to first token stays 4.90 s. At the measured 82 tok/s and an upper bound of 2.5x, a 150-token caption finishes 1.1 s sooner, a 600-token plan 4.4 s sooner and a 1,500-token `run_steps` batch 11.0 s sooner, all at double the price **[computed]**. Because fast and standard requests do not share cached prefixes, mixing them in one session pays for two prefixes. Fast mode belongs on the escalation tier when the expected output is an action plan, chosen once per session. Sonnet 5.5 deserves a benchmark even though the brief named Haiku and Opus. At 1.40 s it has the lowest measured TTFT, which makes it the obvious candidate for the conversational tier that answers a person's spoken question.

Gemini Live is not the cheap, instant baseline it appears to be. Its `gemini-3.8-live` model takes JPEG or PNG stills at most once per second over a stateful WebSocket. Google recommends 768×768 frames ([Live guide](https://ai.google.dev/gemini-api/docs/live-guide), [Vertex streams](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/send-audio-video-streams)). It prices video at $1 per million tokens, or $0.002 a minute ([Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)) **[doc]**. Google's own documents disagree on what a frame costs: 70 tokens per frame at default resolution ([Media resolution](https://ai.google.dev/gemini-api/docs/media-resolution)) against 258 tokens per second of video ([Vertex sessions](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api/start-manage-session)). The $0.002-a-minute price implies about 33 tokens a second, which matches neither **[computed]**. Vertex also says each turn bills all context tokens ([Vertex best practices](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/best-practices)). One developer saw about 1M tokens an hour in AI Studio and about 9M in Cloud billing for the same session ([forum](https://discuss.ai.google.dev/t/gemini-live-2-5-token-counting-what-is-the-expected-cost-of-long-running-video-session/99245)) **[3P]**. Audio-plus-video sessions stop after 2 minutes without context compression, and connections last about 10 minutes ([Session management](https://ai.google.dev/gemini-api/docs/live-session)) **[doc]**. Google publishes no latency figure. Community reports range from about 100 ms to 5–6 s ([LiveKit community](https://community.livekit.io/t/how-to-fix-latency-3-secs-of-gemini-3-1-flash-live/766), [Google AI forum](https://discuss.ai.google.dev/t/live-api-5-6-second-response-latency/123254)) **[3P]**. **Gemini Live's real advantage is voice turn-taking, not visual reaction.** It has native audio, voice-activity detection, barge-in and non-blocking function calls, while its picture of the screen is a 1 fps or slower sampler, just like the design recommended here.

## Shipped systems already sample sparsely and wake on events

The products that look like continuous screen sharing turn out to be samplers. Pipecat throttles Gemini Live video to one frame a second in code ([Pipecat source](https://reference-server.pipecat.ai/en/stable/_modules/pipecat/services/google/gemini_live/llm.html)). LiveKit Agents sends 1 fps while the user speaks and one frame every 3 s otherwise, treating video as "passive" so that it never triggers a turn ([LiveKit video docs](https://docs.livekit.io/agents/multimodality/vision/video.md)). Google's reference web console sends 0.5 fps at quarter scale ([ControlTray.tsx](https://github.com/google-gemini/live-api-web-console/blob/main/src/components/control-tray/ControlTray.tsx)) **[3P, source code]**. Microsoft says Copilot Vision processes shared screens "as a series of images" and "can't take action" ([Microsoft support](https://support.microsoft.com/en-au/microsoft-365-copilot/how-vision-microsoft-365-works)). Gemini in Chrome's Go Live shares the tab's page content rather than its pixels ([Chrome Help](https://support.google.com/chrome/answer/16363185?hl=en)) **[doc]**. The cheapest "screen share with Claude" in the wild is Clicky, a macOS menu-bar app with about 7.8k stars. On each push-to-talk utterance it sends one screenshot and the transcript to Claude, speaks the reply through ElevenLabs, and lets Claude point an overlay cursor with `[POINT:x,y]` tags ([farzaa/clicky](https://github.com/farzaa/clicky)) **[3P]**. That maps directly onto this server's `screenshot` and `agent_pointer` tools.

Continuous recorders show what the gate should look like. screenpipe replaced fixed-rate polling with capture on app switch, focus, click, typing pause, scroll stop and clipboard events. Its default debounce is 200 ms, it runs a pixel-diff check every 3 s with a 5% threshold, and it captures at least every 30 s when idle ([event_driven_capture.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-engine/src/event_driven_capture.rs)). Its OCR gate crops to the union of detected text and runs OCR only when that crop's pixels changed. Every capture pays 10–20 ms of detection and 1–3 ms of hashing, while OCR's hundreds of milliseconds run only on real change. Earlier heuristics "each produced wrong skips": stability waits starved surfaces that never stop changing, and region hashes missed text the detector had not boxed ([ocr_gate.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-capture/src/ocr_gate.rs)) **[3P, source code]**. Peekaboo's `capture live` adds hysteresis: separate idle and active frame rates, a whole-frame change threshold that switches to the active rate, and heartbeat keyframes so that small edits still surface ([Peekaboo capture.md](https://raw.githubusercontent.com/openclaw/Peekaboo/main/docs/commands/capture.md)). The OS already provides the cheapest first gate. ScreenCaptureKit marks frames `idle` when "the display didn't change" and reports `dirtyRects` for changed regions ([SCFrameStatus](https://developer.apple.com/tutorials/data/documentation/screencapturekit/scframestatus.json), [dirtyRects](https://developer.apple.com/tutorials/data/documentation/screencapturekit/scstreamframeinfo/dirtyrects.json)). UI Automation pushes focus, structure and property events, but warns that some "may be raised even when the state of the UI has not changed" ([UIA events](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-eventsoverview)) **[doc]**.

The evidence on what the model should receive points to text deltas, not trees. OSWorld-Human measured 3–26 s per step just to generate an accessibility tree, and in LibreOffice Calc a tree-only agent took 50 steps against 14 for screenshots and 10 for tree plus Set-of-Marks ([OSWorld-Human](https://arxiv.org/html/2506.16042v1)). UFO2 found UI Automation and vision complementary: 27.9–56.7% of OmniParser's detections duplicated UIA controls, and hybrid detection recovered 9.9–25% of what UIA missed ([UFO2](https://arxiv.org/html/2504.14603)) **[3P]**. Small local models are fast enough to act as a first-pass filter. FastVLM reports about 85x faster time to first token than LLaVA-OneVision at the same size ([FastVLM](https://arxiv.org/html/2412.13303v2)). But **no shipped desktop agent was found using a local VLM as a gate in front of a frontier model**, so that tier is an experiment, not prior art. The experience also warns about event subscriptions. Windows-MCP ships its UIA WatchDog off by default because "its long-lived UIA subscription can crash the server" ([Windows-MCP README](https://raw.githubusercontent.com/CursorTouch/Windows-MCP/main/README.md)), and screenpipe throttles accessibility walks per app once a walk takes more than 50 ms ([budget.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-a11y/src/budget.rs)) **[3P]**.

## The repository already holds most of a watcher, minus the stream and the push

The capture path is one still per request on every platform. On macOS a warm Swift helper calls `SCScreenshotManager.captureImage`, rebuilding the filter and configuration each time. Its `serve` loop awaits each command before it reads the next line (`libexec/macos-agent-helper.swift:397-419`) **[code]**. Every helper call is serialised in-process and across servers through `~/Library/Caches/computer-use-mcp/helper.lock`, which fails with `helper_busy` (`src/session/macos-helper.ts:239`, `:262`) **[code]**. The lock exists because two concurrent ScreenCaptureKit captures hung each other. On Windows the DXGI duplication stays open per monitor, but `AcquireNextFrame` fills a `DXGI_OUTDUPL_FRAME_INFO` that nothing reads, so the dirty rectangles and present times a gate would want are discarded (`native/src/capture_win.rs:140-142`, plus a search for `info.` in that file) **[code]**. Windows.Graphics.Capture builds and closes a session per call (`native/src/capture_win.rs:404-427`) **[inventory]**. **A search of `native/src`, `libexec` and `src` finds no `SCStream` instance, no `ThreadsafeFunction`, no `AXObserver`, no `AddAutomationEventHandler` and no `SetWinEventHook`** **[code]**. Native code therefore cannot push frames or events to JavaScript, and no accessibility event reaches the server at all.

The change detection that exists works on exact hashes and runs only inside a tool call. `ScreenshotHandler` keeps the last hash, scope and image-to-screen mapping. It answers an identical capture with text for up to `UNCHANGED_TEXT_REPEATS = 3` repeats (`src/session/screenshot-handlers.ts:32`, `:105-127`, `:216-226`) **[code]**. `wait_for_stable` polls 800 px captures every 250 ms, `wait_for_text` polls OCR, `wait_for_window` re-lists windows every 250 ms, and `verify: true` hashes before and after an action (`src/session/agent-desktop-handlers.ts:311-361`, `:242-307`, `:427-458`; `src/session/input-handlers.ts:330-353`) **[inventory]**. None emits progress, and none runs between calls. Outside a tool call the server can push almost nothing. Resource updates fire only from the registry's `afterToolCall` (`src/server.ts:278-303`) **[code]**. HTTP hosts with a broker or a custom authoriser refuse `subscriptions/listen` outright (`src/server.ts:387-393`) **[code]**. The tasks bridge stubs `notify` and `log` to no-ops (`src/mcp-tasks.ts:249-250`) **[code]**. The brokered deployments that run a console are therefore exactly the ones that cannot subscribe.

The run console is the nearest thing to a shared live view: an MCP App with a transcript, a plan, the latest frame and a composer whose messages become `user` turns. It is a narrated slideshow, though, not a stream. Frames appear only when the agent calls `run_progress {capture: true}`, the reference host polls `run_console` every 900 ms (`src/run-console-host.ts:146`), and the app's CSP forbids every network connection (`src/agent-run.ts:858`) **[code]**. This pass found one new defect there. The console's capture closure calls `session.dispatch('screenshot', {quality: 70})` without `resend` (`src/server.ts:319-326`) **[code]**. On a still screen, dedup returns text instead of an image, so the closure returns `null` and attaches nothing. **Five consecutive `run_progress {capture: true}` calls on an unchanged screen attached a fresh frame only on the first and fifth; the three in between returned no image, and the console kept the first frame's timestamp** **[script]**. A person watching cannot tell "nothing changed" from "nothing was captured". A live view would hit this constantly.

The person-control layer is the strongest reusable asset. It has a state machine with Pause, Resume and Stop, a card excluded from capture, takeover detection, an emergency chord, a user-active guard and named refusals for a locked screen, all on by default on macOS (`src/session/operator-control.ts`, `native/src/activity.rs`) **[inventory; tested in `test/v7.7-person-control.test.mjs`]**. It was built for an agent that acts, and two of its rules make a watch-only session invisible. The card launches only on a mutating call, and takeover detection is armed only while one runs. `begin` launches the presenter only `if (options.mutates !== false)` and arms takeover only `if (options.mutates)` (`src/session/operator-control.ts:274-279`). The session passes `mutates` straight through (`src/session.ts:800`), and it holds the display awake only for mutating calls (`src/session.ts:797`) **[code]**. **A session that only watches today shows no card at all.** A live mode must add a visible "watching" state before anything else ships. One template for turning pull-only signals into events already exists: `DesktopSupervisor` runs a worker thread that loops on the native emergency-stop latch and the idle clock and posts `takeover` messages to the main thread (`src/supervisor-worker.ts:1-25`) **[code]**. The same pattern can carry frame-changed and window-changed events without adding `ThreadsafeFunction` to the addon. The stated direction already leans this way. The v8 plan's last item is a supervision panel at 1–2 fps (`docs/specs/v8-app-bridges/requirements.md:83-87`). The competitor study scheduled a persistent `SCStream` for 7.8 (`docs/reviews/2026-10-23-competitor-study.md:226`). The gaming review argued to "sample and synchronise rather than stream" (`docs/reviews/2026-10-25-gaming-computer-use.md:41`) **[code]**.

## Recommended architecture: stream locally, gate, tier, and keep the person in charge

The design has five layers. A persistent capture source never leaves the machine. A change gate decides when anything is worth a model's attention. An observer turns gate output into events. A driver loop in a host the project controls turns events into model calls. The existing person-control layer, extended to cover watching, wraps all of it.

```
screen ─► persistent capture (SCStream / DXGI + kept-open WGC / PipeWire)
            ├─► person's live view, 1–2 fps, never sent to a model
            └─► change gate: OS idle + dirty rects ─► downscaled hash ─► tolerance
                             ─► window list ─► OCR / accessibility text delta
                             (200–500 ms debounce, idle floor, heartbeat)
                    │ event {kind, region, text delta, frame id}
                    ▼
            observer (worker thread) ─► resourceUpdated · channel text · console push
                    ▼
host driver: Haiku 5.5 triage (thinking off, no tools) ──escalate──► Opus 5.5 or Sonnet 5.5
             (caption + relevance)                                    (tools: run_steps, click_text …)
                    ▲                                                          │
person: voice → STT / typed turns / takeover / Pause · Stop ◄── status card "watching" + run console
```

The tiers have strict roles. **The triage tier watches and never acts.** Haiku 5.5 runs with thinking disabled, low effort and no tools. It receives the gated crop, frame or text delta and returns a short caption with a relevance decision, which keeps an injected instruction on screen from reaching any tool. **The escalation tier acts only for the person.** Opus 5.5 takes the events triage flags and the person's own requests, with the latest frame, the recent captions and the full tool surface. Fast mode is reserved for sessions whose escalations emit long action plans. Every action it takes passes the same dispatch gates, guard and Pause/Stop as today. A person's spoken or typed question bypasses triage and goes straight to the conversational tier; the candidate is Sonnet 5.5 at low effort with `between_tools` if Phase 0 confirms its latency with images. The watch itself is opt-in, started by the person (as Copilot Vision and Chrome's Go Live are), scoped to a session, shown on the card, and stopped by a locked screen, Stop, battery saver or the emergency chord. Frames stay in memory, as the run store already guarantees for console frames (`src/agent-run.ts:196-290`) **[inventory]**.

Each host gets the subset it can carry. In the project's own host (`computer-use-mcp-console`, extended into a driver that calls the Anthropic API), the whole design works, and the host subscribes to the observer in-process rather than through `subscriptions/listen`, which restricted hosts refuse. In Claude Code, a separate legacy-handshake stdio channel server can post short text events such as "a Save dialog opened in TextEdit", which Claude reads on its next turn and answers by calling `screenshot` or `read_window_text` on the main server. In Claude Desktop, Cursor and VS Code, an MCP App panel can poll an app-only frame tool every 0.5–2 s for the person and write the latest caption through `ui/update-model-context`. The model there sees pixels only when it calls a tool. Everywhere, actions and results flow back through the existing tools and result contract, which already tells the model what landed.

## The screen becomes an input channel, and other risks

**Prompt injection grows from a pull risk into a push risk.** Today the model sees a screenshot only when it asks for one. In a live mode, anything that can put text on the screen gets a turn: a web page, an incoming chat, an email preview, a notification toast. Brave showed nearly invisible light-blue text in a screenshot steering Perplexity Comet to an attacker URL ([Brave](https://brave.com/blog/unseeable-prompt-injections/)) **[3P]**. Anthropic says classifiers "automatically scan what the tools return, such as screenshots" ([Computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool.md)) **[doc]**, but nothing says whether frames sent as user-turn images in a custom driver loop are scanned too. The design answers structurally. The triage tier has no tools. Frame-derived text is labelled untrusted and can never change a target, a plan or an approval. Actions start only from the person or from an escalation the person can see on the card. The card and pointer are already excluded from capture so that on-screen text cannot point the agent at its own controls.

**Privacy risk concentrates when capture becomes continuous.** Frames leave the machine for Anthropic's API. Copilot Vision keeps shared audio and video for 48 hours ([Microsoft support](https://support.microsoft.com/en-au/microsoft-365-copilot/how-vision-microsoft-365-works)). Recall needed local-only processing, a VBS enclave and a sensitive-data filter, which testers reported missing unlabelled card numbers ([Microsoft support](https://support.microsoft.com/windows/d404f672-7647-41e5-886c-a3c59680af15), [Reclaim The Net](https://reclaimthenet.org/microsoft-recall-privacy-risks-sensitive-data-exposure)). screenpipe's PII filter "can miss sensitive information" and does not filter images ([screenpipe](https://screenpipe.com/privacy-filter)) **[doc; 3P]**. Text filters are therefore a backstop, and exclusion must happen at the source, before the gate or OCR: credential managers on the existing sensitive-app list, windows marked `NSWindowSharingNone` or `WDA_EXCLUDEFROMCAPTURE`, private browsing, and accessibility fields marked `sensitive`. Voice adds a microphone permission and a third-party speech processor, because Anthropic offers no audio API. Recording what the person does, beyond counts and timing, raises questions the codebase has deliberately avoided: the card never shows typed text.

**Battery and CPU are unmeasured for this design and for every design like it.** No source measures energy per hour for any continuous screen-capture agent. screenpipe reports about 5–10% CPU and about 600 MB of RAM ([architecture](https://docs.screenpipe.com/architecture)), and an older issue reports over 100% CPU and over 10 GB of RAM while the app called itself healthy ([screenpipe#183](https://github.com/mediar-ai/screenpipe/issues/183)). Its power profiles relax capture as the battery drains and pause everything at 10% ([profile.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-engine/src/power/profile.rs)) **[3P]**. In this repository the warm helper stayed flat at 27.4–27.8 MB over 200 captures (`docs/specs/v7.7/tasks.md:74`) **[inventory]**, but nothing has measured a stream left open for an hour. Phase 0b must, and the watcher needs the same battery-aware profile and a hard stop at a locked screen.

**Host and platform gaps can strand the design.** Claude Code channels are a research preview, refused on 2026-07-28 connections ([MCP docs](https://code.claude.com/docs/en/mcp)), and gated behind an allowlist or a development flag ([Channels](https://code.claude.com/docs/en/channels)). MCP Apps can regress in a host release, as Cursor 3.10.20 shows. No host documents whether `ws://localhost` is allowed in `connectDomains`, or which hosts accept images through `ui/update-model-context` **[doc]**. Inside the server, a stream held by one server would starve every other server's captures under the cross-server lock unless captures are served from the stream. The cost cliffs matter too: Haiku's 5x price above 100K prompt tokens, a cache prefix lost whenever thinking, effort or speed changes, and fast and standard requests never sharing a cache.

Ten questions remain open, and each has a way to close it. Five are measurements. The first is the latency of Haiku 5.5 with thinking off, Sonnet 5.5 with `between_tools`, and Opus 5.5 fast with an image in the prompt, which decides the tiers. The last is a product decision only the maintainer can make: whether the model should ever be told what the person did on screen, beyond the fact that they acted.

## Conclusion

The question "can the server stream the screen to Claude?" turns out to ask about the wrong component. Capture is already fast enough: 62 ms warm, and about 17 ms per frame from a stream. What a live mode lacks sits at the two ends. At the model end, Claude has no session and multi-second first tokens. At the host end, nothing lets a server start a model turn. The server's real contribution is deciding *when* a model should look and *what* it should see. That is a gate, not a pipe, and the same gate serves the agentic roadmap already planned for 7.8: animation-tolerant waits, action-bound frames and the supervision panel. Building it for live sharing is therefore not a detour. Tiering also changes the economics in a way the frame-cost framing hides. On Opus 5.5, thinking and output are most of every call's price, so the number of escalations, not pixels, decides the bill, and a no-tools Haiku triage tier earns its place twice: as the cheapest filter and as the injection firewall.

The other shift is in what the person-control layer is for. Pause, Stop, takeover, the chord and the card were built to restrain an agent that acts. In a live mode they become the privacy contract for an agent that watches. The code today hides a watch-only session from the person, which is the one thing that contract cannot allow. Gemini Live's lead is real but narrow. It lies in voice turn-taking, not in seeing the screen, and its own pipeline samples stills at 1 fps or slower and bills context per turn. A Claude loop that gates sharply, triages cheaply and escalates rarely can match its visual responsiveness at a comparable hourly cost. It needs a host the project controls, and Phase 0 has to confirm the latency of the tiers it would use.
