# Realtime multimodal model APIs with live screen or video input (as of 2026-10-25)

Research notes, collected 2026-10-25. Google pages fetched were "last updated" between 2026-10-06 and 2026-10-22 UTC unless noted. Several vendor docs disagree with each other; the disagreements are listed where they appear rather than resolved.

## Gemini Live API: current models, transport, how frames are sent, and what a frame costs in tokens

### Takeaway
In October 2026 the current Gemini Live models are `gemini-3.8-live` and `gemini-3.8-live-extended-thinking` (GA 2026-09-15), with `gemini-3.1-flash-live-preview` now marked legacy. All of them use one stateful WSS connection (`BidiGenerateContent`). Screen or camera video is not a video stream: the client sends individual JPEG or PNG frames in `realtimeInput.video`, at most 1 frame per second, at a recommended 768x768. Google's docs give two different per-frame token costs: 70 tokens per frame at the default resolution for Gemini 3/4 on the media-resolution page, and 258 tokens per second of video on the Vertex session page. Audio costs 25 tokens per second in both.

### Cited Findings

**Models (Gemini Developer API)**
- `gemini-3.8-live` (Stable/GA) is "the default Live API model for low-latency voice agents without reasoning delays". `gemini-3.8-live-extended-thinking` (Stable/GA) is the one to use when more background reasoning is needed. `gemini-3.1-flash-live-preview` is a "Legacy Live API preview model. We recommend updating to Gemini 3.8 Live." `gemini-2.5-flash-native-audio-preview-12-2025` is still listed and not deprecated, but only users who have used the 2.5 models before can access it — [Gemini models](https://ai.google.dev/gemini-api/docs/models)
- Changelog dates: 2026-09-15, Gemini 3.8 Live and 3.8 Live Extended Thinking released as "two new audio-to-audio models for real-time voice applications using the Live API", with "default asynchronous function calling". 2026-03-26, `gemini-3.1-flash-live-preview` released. 2025-12-12, `gemini-2.5-flash-native-audio-preview-12-2025`. 2025-09-23, `gemini-2.5-flash-native-audio-preview-09-2025`. Shut down: `gemini-2.5-flash-preview-native-audio-dialog` and `gemini-2.5-flash-exp-native-audio-thinking-dialog` (by 2025-10-20), then `gemini-2.0-flash-live-001` and `gemini-live-2.5-flash-preview` (2025-12-09) — [Gemini API changelog](https://ai.google.dev/gemini-api/docs/changelog)
- Other Live-API endpoints on the models and pricing pages: `gemini-3.5-live-translate-preview` (speech-to-speech translation), `gemini-3.5-transcribe-live` (streaming speech-to-text, 2026-08-26) and `gemini-robotics-er-2-streaming-preview` (2026-07-30, "real-time text streaming using the Live API") — [Gemini models](https://ai.google.dev/gemini-api/docs/models); [changelog](https://ai.google.dev/gemini-api/docs/changelog)
- `gemini-3.8-live` model card: input text, images and audio; output text and audio; input limit 131,072 tokens and output limit 65,536. Supports function calling, Search grounding, Live API, audio generation and interleaved thinking. Does not support caching, code execution, file search, Google Maps grounding, structured outputs, URL context or Batch. The card's latest update is September 2026 — [Gemini 3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)
- Migrating from 3.1 Flash Live: change the model string, remove `thinking_level`/`thinking_config` (3.8 Live does not support them, because its thinking is interleaved), and turn on output audio transcription to get a text transcript — [Gemini 3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live); [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)
- Thinking levels: 3.8 Live Extended Thinking accepts `low`, `medium` or `high` (not `minimal`). 3.1 Flash Live defaults to `minimal`. With extended thinking, `turnComplete: true` does not mean the session is idle; check `interaction_status` (`IN_PROGRESS` vs `IDLE`) — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)
- A Google launch blog post for 3.8 Live was not found. A third-party blog reports "Gemini 3.8 Live with Live Avatar" was announced 2026-09-24 through Gemini Enterprise, and Vercel AI Gateway availability is reported from 2026-09-17. Both are unverified secondary sources — [jetstream.blog](https://jetstream.blog/?p=224844); [techbytes.app](https://techbytes.app/posts/gemini-38-live-models-now-available-on-ai-gateway/)

**Models (Vertex AI / "Gemini Enterprise Agent Platform")**
- Supported models table: `gemini-3.8-live` (GA, "Recommended", with live avatar), `gemini-live-2.5-flash-native-audio` (GA, "Recommended") and `gemini-3.5-transcribe-live-preview` (Preview, speech-to-text only) — [Vertex Live API overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api)

**Transport and auth**
- Transport: "Stateful WebSocket connection (WSS)". Input can be audio, images and text; the native-audio models output audio only (text comes through transcription) — [Live API overview](https://ai.google.dev/gemini-api/docs/live); [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)
- Endpoint: `wss://generativelanguage.googleapis.com/ws/google.ai.generativelanguage.v1beta.GenerativeService.BidiGenerateContent` ("The URL is for version `v1beta`"). The first message must be `BidiGenerateContentSetup` (`setup.model`, `responseModalities`, `systemInstruction`, ...) — [Live API reference](https://ai.google.dev/api/live); [WebSocket getting started](https://ai.google.dev/gemini-api/docs/live-api/get-started-websocket)
- Ephemeral tokens: created with `POST https://generativelanguage.googleapis.com/v1beta/auth_tokens`, "only compatible with Live API", v1beta only, used against `...BidiGenerateContentConstrained` with an `access_token` query parameter or an `Authorization: Token` header. Defaults: `expireTime` 30 minutes, `newSessionExpireTime` 1 minute. `uses: 1` means "can only be used to start a single session", but the same token can be reused for the 10-minute `sessionResumption` reconnects. `live_connect_constraints` locks the token to a model and config (the example locks `gemini-3.8-live`) — [Ephemeral tokens](https://ai.google.dev/gemini-api/docs/ephemeral-tokens); [WebSocket getting started](https://ai.google.dev/gemini-api/docs/live-api/get-started-websocket)
- Server-to-server auth is the default; client-side apps should use ephemeral tokens — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)

**Sending audio**
- Input is raw 16-bit little-endian PCM at 16 kHz (`audio/pcm;rate=16000`; other rates are resampled). Output is 24 kHz PCM — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide); [Live API overview](https://ai.google.dev/gemini-api/docs/live)
- "Send audio in chunks of 20ms to 40ms"; "Send small chunks (20ms - 100ms) to minimize latency"; do not buffer around 1 second — [Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)
- VAD: automatic VAD is on by default (`realtime_input_config.automatic_activity_detection`). `silence_duration_ms` of 500–800 ms is recommended and the server default is about 800 ms. Manual mode uses `activityStart`/`activityEnd`. `send_realtime_input` "prioritizes responsiveness over deterministic ordering"; `send_client_content` preserves order — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)

**Sending screen or camera frames**
- Overview: image input is "JPEG <= 1FPS" — [Live API overview](https://ai.google.dev/gemini-api/docs/live)
- Guide: frames go as individual JPEG or PNG images through `send_realtime_input(video=types.Blob(...))`, "max 1 frame per second" — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)
- Wire shape: `realtimeInput.video {data: base64, mimeType: "image/jpeg"}`. `realtimeInput.mediaChunks[]` is deprecated ("Use one of `audio`, `video`, or `text` instead"; "all but the first will be ignored") — [Live API reference](https://ai.google.dev/api/live); [WebSocket getting started](https://ai.google.dev/gemini-api/docs/live-api/get-started-websocket)
- Vertex: "supports video frames input at 1 FPS"; "For best results, use 768x768 resolution at 1 FPS". The sample resizes to a 768x768 maximum, JPEG-encodes, and sleeps 1.0 s between frames — [Vertex: Send audio and video streams](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/send-audio-video-streams)
- Firebase AI Logic: video at "1 frame per second", native 768x768 recommended, "rules out fast-changing video, such as high-speed sports". Images up to 7 MB per inline file (PNG, JPEG, WebP, HEIC, HEIF) — [Firebase Live API limits and specs](https://firebase.google.com/docs/ai-logic/live-api/limits-and-specs)
- Google's official sample web console sends screen or webcam frames at 0.5 fps (`setTimeout(sendVideoFrame, 1000 / 0.5)`), scales the canvas to 25% of the source size, and encodes JPEG at quality 1.0 (`canvas.toDataURL("image/jpeg", 1.0)`) — [google-gemini/live-api-web-console ControlTray.tsx](https://github.com/google-gemini/live-api-web-console/blob/main/src/components/control-tray/ControlTray.tsx)
- LiveKit Agents' default video sampler forwards 1.0 fps while the user is speaking and 0.3 fps when the user is silent (`VoiceActivityVideoSampler(speaking_fps=1.0, silent_fps=0.3)`) — [livekit/agents agent_session.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/agent_session.py)
- 3.8 Live sends video frames to the model by default (default turn coverage `TURN_INCLUDES_AUDIO_ACTIVITY_AND_ALL_VIDEO`). Google advises "sending frames only when needed to manage context and cost". The 3.8 Live card does not list video among its input modalities, although it accepts frames as images — [Gemini 3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)

**Token cost per frame and per second**
- Media-resolution table (Gemini 4 and Gemini 3 models): video costs **70 tokens per frame** at unspecified (default), low and medium, and **280 per frame at high** (`ultra_high` does not apply to video). A still image costs 1120 tokens at default, 280 low, 560 medium, 1120 high and 2240 ultra_high. Audio costs 25 tokens per second at every level. The page does not say whether these counts apply to the Live API — [Media resolution](https://ai.google.dev/gemini-api/docs/media-resolution)
- Vertex: "Streaming token rates: **25 tokens per second (TPS)** for audio and **258 TPS** for video" — [Vertex: Start and manage live sessions](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api/start-manage-session). This contradicts the 70-tokens-per-frame figure above.
- Live guide: `media_resolution` (the example uses `MEDIA_RESOLUTION_LOW`) changes per-frame tokens for visual input, while audio is tokenized at a fixed rate whatever the setting. `RealtimeInputConfig` media resolution falls back to `setup.generationConfig.mediaResolution` — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide); [Live API reference](https://ai.google.dev/api/live)
- Usage reporting: `usage_metadata.total_token_count`, with a per-modality breakdown in `response_tokens_details` (`ModalityTokenCount`). The reference also defines `promptTokenCount`, `cachedContentTokenCount`, `toolUsePromptTokenCount` and `thoughtsTokenCount` — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide); [Live API reference](https://ai.google.dev/api/live)

### Inferences
- "Screen sharing" in Gemini Live is a client-side frame sampler that sends discrete stills at 1 fps or slower over the same socket as the audio. Nothing at the API level is a video codec or a WebRTC video track (Gemini has no WebRTC transport at all). A desktop MCP server that already captures window JPEGs, such as this project's ScreenCaptureKit helper, produces exactly the input the Live API takes.
- 258 tokens per second matches the old Gemini 1.5/2.x convention of 258 tokens per image at 1 fps. The 70 tokens per frame figure is the Gemini 3/4 one. For 3.8 Live, 70 per frame is more likely correct, but the Live-specific docs never say which applies. Confirm by reading `usage_metadata` on a test session.
- Google's own sample uses 0.5 fps and LiveKit uses 0.3 fps when the user is silent. The practical default is lower than the 1 fps ceiling, and frame rate follows voice activity.

### Gaps
- No official statement of how many tokens a Live video frame costs on 3.8 Live specifically, or whether `media_resolution` high (280 per frame) is allowed in Live.
- No published maximum JPEG byte size for Live frames (Firebase's 7 MB inline-file limit is generic), and no statement of what happens to frames sent faster than 1 fps (dropped, throttled or rejected).
- The 768x768 recommendation appears only in Vertex and Firebase docs, not on ai.google.dev.

## Live session limits: duration, compression, resumption, concurrency, rate limits

### Takeaway
Without context compression a session is capped at 15 minutes for audio only and **2 minutes for audio plus video**. Each WebSocket connection lasts about 10 minutes. Long screen-sharing sessions therefore need both sliding-window compression and session resumption. Vertex documents 1,000 concurrent sessions per project; the Gemini Developer API publishes no Live concurrency numbers outside AI Studio.

### Cited Findings
- "Without compression, audio-only sessions are limited to 15 minutes. Audio-video sessions are limited to 2 minutes." Compression can extend a session to "an unlimited amount of time". Going over a limit ends the session and its connection — [Session management](https://ai.google.dev/gemini-api/docs/live-session)
- A connection lasts around 10 minutes, and the session ends with it unless resumption is used — [Session management](https://ai.google.dev/gemini-api/docs/live-session). Vertex: "Default maximum conversation session length: 10 minutes", extendable with goAway and resumption — [Vertex: Start and manage live sessions](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api/start-manage-session)
- Context window: 128k tokens for native-audio models and 32k for other Live models — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide). The 3.8 Live card gives an input limit of 131,072 — [Gemini 3.8 Live](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live). Vertex: "128k tokens" for all Live models — [Vertex: Start and manage](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api/start-manage-session)
- Compression (`contextWindowCompression`): `triggerTokens` defaults to "80% of the model's context window limit"; `slidingWindow.targetTokens` defaults to "trigger_tokens/2" — [Live API reference](https://ai.google.dev/api/live). Vertex gives the allowed ranges, `trigger_tokens` 5,000–128,000 and `target_tokens` 0–128,000; its example uses 10,000/512. Compression "prunes or summarizes the oldest turns" — [Vertex: Start and manage](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api/start-manage-session). Vertex also warns that "Context compression will cause conversation history loss" — [Vertex best practices](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/best-practices)
- Session resumption: the server sends `SessionResumptionUpdate` (`newHandle`), and the client reconnects with `SessionResumptionConfig.handle`. Developer API: handles are "valid for 2 hours after the last session termination" — [Session management](https://ai.google.dev/gemini-api/docs/live-session); [Best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices). Vertex: "You can resume a previous session within 24 hours", with a reconnect window after disconnect of "typically around 10 minutes" — [Vertex: Start and manage](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api/start-manage-session). These two windows conflict (2 h vs 24 h).
- The API reference describes handles as coming from "`SessionResumptionUpdate.token`" while the message field is `newHandle`, an internal inconsistency in the docs — [Live API reference](https://ai.google.dev/api/live)
- GoAway carries `timeLeft` before the connection ends with ABORTED; it "will never be less than a model-specific minimum" — [Live API reference](https://ai.google.dev/api/live). Vertex and Firebase say goAway comes 60 seconds before the end — [Vertex: Start and manage](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api/start-manage-session); [Firebase limits](https://firebase.google.com/docs/ai-logic/live-api/limits-and-specs)
- Concurrency (Vertex): "up to 1,000 concurrent sessions per project on the pay-as-you-go (PayGo) plan", not applicable to Provisioned Throughput — [Vertex: Start and manage](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api/start-manage-session). Firebase on Vertex: 1,000 concurrent sessions per project and 4M tokens per minute — [Firebase limits](https://firebase.google.com/docs/ai-logic/live-api/limits-and-specs)
- Concurrency (Developer API): the rate-limits page lists no Live models and no concurrent-session, TPM or RPD numbers; limits "can be viewed in Google AI Studio". The only general figures are spend caps per 10-minute window: Tier 1 $10, Tier 2 $50, Tier 3 $200 — [Rate limits](https://ai.google.dev/gemini-api/docs/rate-limits). Firebase says Developer API concurrent-session and TPM limits "vary by usage tier" without numbers — [Firebase limits](https://firebase.google.com/docs/ai-logic/live-api/limits-and-specs)
- Anecdote (not official): a developer reports handshake 409s on a Tier 2 project running only a few sessions, which they attribute to orphaned sessions still counting during a grace period — [Google AI forum](https://discuss.ai.google.dev/t/gemini-3-5-live-translate-preview-in-production-paid-tier-measured-concurrency-dashboard-409s-vs-real-409s-silent-stalls-and-session-birth-degradation-data-6-questions/180489)

### Inferences
- The 2-minute audio+video cap fits the old 32k context at 258 video + 25 audio tokens per second: 32,000 / 283 ≈ 113 s. On a 128k model at 70 tokens per frame, the context would last roughly 20 minutes. The 2-minute figure may be a legacy number carried forward, but the docs still state it, so plan for it.
- A 1-hour screen share needs (a) `contextWindowCompression` on, (b) `sessionResumption` on and a reconnect at least every ~10 minutes (around 6 reconnects per hour) driven by GoAway, and (c) acceptance that older frames and dialogue are pruned or summarized.

### Gaps
- No published Developer API concurrent-session caps per tier (AI Studio only).
- Whether the 15/2-minute limits differ for 3.8 Live: no page gives 3.8-specific session limits.
- Whether compression summarizes or simply drops old video frames.

## Latency: published or measured time to first audio

### Takeaway
Google publishes no millisecond latency figure for any Live model, only qualitative claims ("ultra-low latency audio-to-audio"). Community measurements range from about 100 ms time to first token in a favourable setup to 3–7 s with tools or poor VAD settings. End-of-speech detection and enabled tools such as Google Search dominate.

### Cited Findings
- 3.8 Live is described as offering "ultra-low latency audio-to-audio interactions" and real-time dialogue "without reasoning-induced delays", with no numbers — [Gemini 3.8 Live](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)
- The Live overview says only "low-latency", and that client-to-server "generally offers better performance for streaming audio and video" — [Live API overview](https://ai.google.dev/gemini-api/docs/live). Vertex gives qualitative claims only — [Vertex Live API overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api)
- VAD guidance: `silence_duration_ms` of 100–200 ms splits utterances, 2000 ms or more adds latency, and the server default is about 800 ms — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)
- Community: response delays of about 5–6 s on Live — [Google AI forum](https://discuss.ai.google.dev/t/live-api-5-6-second-response-latency/123254). Native-audio latency grows during long sessions — [Google AI forum](https://discuss.ai.google.dev/t/gemini-live-api-native-audio-response-latency-gradually-increases-during-long-sessions/115508). A Gemini 3.1 Flash Live setup on LiveKit had about 2–2.5 s time to first token, dropping to about 100 ms (1–1.5 s end to end) after removing the Google Search tool — [LiveKit community](https://community.livekit.io/t/how-to-fix-latency-3-secs-of-gemini-3-1-flash-live/766)

### Inferences
- For a desktop agent, latency from "frame on screen" to "model reacts" is at least the frame interval (1–3 s at 1–0.3 fps), plus end-of-turn detection (around 0.8 s by default), plus model time. Sub-second visual reaction is not what this API is built for.

### Gaps
- No vendor benchmark of time to first audio for 3.8 Live, and no measurement of latency added by video frames in context.

## Tool calling during a Live session (functions, async, Search, code execution, computer use)

### Takeaway
Live sessions support client-executed function calling and Google Search grounding; Live has no code execution, URL context or Computer Use tool. On 3.8 Live, function calls are non-blocking by default: the model keeps talking while the client runs the tool, and the client sends results back with a scheduling hint (`SILENT`, `WHEN_IDLE`, `INTERRUPT(ED)`). The model can call any function the client declares, so "act on what it sees" means the client declares its own desktop-action functions. Gemini's Computer Use tool exists only on the Interactions API with non-Live models.

### Cited Findings
- Function declarations go in the session config. The client returns `FunctionResponse` objects through `send_tool_response`/`sendToolResponse`. "Unlike the generateContent API, the Live API doesn't support automatic tool response handling." One prompt can produce several function calls — [Live tool use](https://ai.google.dev/gemini-api/docs/live-tools)
- `FunctionResponse` objects are matched to `FunctionCall`s by `id` — [Live API reference](https://ai.google.dev/api/live)
- 3.8 Live: "`NON_BLOCKING` by default". Blocking mode and scheduling (`SILENT`, `WHEN_IDLE`, `INTERRUPTED`) are supported. Extended Thinking is `NON_BLOCKING` only, with no blocking mode or scheduling. 3.1 Flash Live is sequential only: "The model won't respond until the tool response is sent" — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide); [Gemini 3.8 Live](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)
- Scheduling semantics: `INTERRUPT` stops the model's current activity and reports the result immediately; `WHEN_IDLE` waits until the model finishes its current activity; `SILENT` uses the result later without announcing it — [Live tool use](https://ai.google.dev/gemini-api/docs/live-tools). (The live-tools page spells it `INTERRUPT`; the guide and 3.8 card spell it `INTERRUPTED`.)
- On interruption (barge-in), generation is discarded, `server_content.interrupted` is true, and "Pending function calls are discarded", with the server reporting the cancelled call IDs — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)
- The support table on the live-tools page still covers only 3.1 Flash Live and 2.5 Flash Live: Search supported on both; function calling "synchronous only" on 3.1 and "synchronous and asynchronous" on 2.5; Google Maps, code execution and URL context "Not supported" on both. The same page's prose also mentions model-generated code running "in a sandbox", which contradicts its own table — [Live tool use](https://ai.google.dev/gemini-api/docs/live-tools)
- 3.8 Live card: function calling and Search grounding supported; code execution, Maps grounding and URL context not supported — [Gemini 3.8 Live](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live). Firebase lists "Grounding with Google Maps" as a Live tool, which conflicts with this — [Firebase limits](https://firebase.google.com/docs/ai-logic/live-api/limits-and-specs)
- Search billing: "A customer-submitted request to Gemini may result in one or more queries to Google Search", and each query is charged — [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)
- Computer use: the live-tools page and the 3.8 Live card do not mention it — [Live tool use](https://ai.google.dev/gemini-api/docs/live-tools); [Gemini 3.8 Live](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live). The Computer Use tool is documented for `gemini-4-argon`, `gemini-3.8-flash` ("The recommended model for computer use"), `gemini-3.5-flash-lite` and `gemini-3-flash-preview`, with examples only on the Interactions API (`/v1beta/interactions`). Actions include click, double/triple/middle/right click, move, type, drag_and_drop, press_key, hotkey, scroll and take_screenshot for desktop and browser. Coordinates are integers in 0–999 (normalized 1000x1000), and a `safety_decision: require_confirmation` must be put to the end user — [Computer Use](https://ai.google.dev/gemini-api/docs/computer-use)
- Tool prompting: "The model performs best when each task involves single function calls"; prompt chaining is recommended over long prompts — [Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)
- Vertex lists "tool use (function calling and Google Search)" as a Live feature — [Vertex Live API overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api)

### Inferences
- An MCP desktop server can sit behind a Live session as the executor of client-declared functions: the Live client turns MCP tools into `functionDeclarations`, runs the MCP call on each `toolCall`, and returns a `FunctionResponse`. Live has no native MCP support, unlike OpenAI Realtime. With 3.8 Live's non-blocking default, a slow desktop action such as a `wait_for_stable` does not freeze the voice conversation. `SILENT` suits a status result the model should not narrate.
- Clicking on "what it sees" in Live means the model reads coordinates from a ≤1 fps, possibly downscaled (768x768) JPEG. Unlike the Computer Use tool, Live has no trained coordinate convention, so grounding accuracy is unknown. Semantic targets (accessibility, OCR such as `click_text`) are likely more reliable than coordinates read from Live frames. This is untested.
- Barge-in discards pending function calls. A desktop action already in flight in the MCP server is not cancelled automatically; the client must map the reported cancelled IDs to MCP cancellation.

### Gaps
- No 3.8 Live-specific tool support table (the live-tools page still describes 3.1/2.5).
- No documentation of whether a model can be given a tool result containing an image (a screenshot) in Live, as opposed to text JSON.

## Pricing for Live models and a worked estimate for 1 hour of screen sharing

### Takeaway
On the Gemini Developer API, 3.8 Live (same price as 3.8 Live Extended Thinking and 3.1 Flash Live) costs **$0.75/M text input, $3.00/M audio input ($0.005/min), $1.00/M image/video input ($0.002/min), $4.50/M text output and $12.00/M audio output ($0.018/min)**, and the free tier is free of charge. Google also states that **each turn bills all context tokens** (history plus system instruction). One hour of screen sharing therefore costs about $0.5–1.3 if every token were billed once, but plausibly $2–35 depending on turn frequency and compression settings.

### Cited Findings
- Developer API Standard tier, per 1M tokens: `gemini-3.8-live`, `gemini-3.8-live-extended-thinking` and `gemini-3.1-flash-live-preview` cost input text $0.75, input audio $3.00 "or $0.005/min", input image/video $1.00 "or $0.002/min", output text $4.50, and output audio $12.00 "or $0.018/min". Free tier input and output are "Free of charge". Only a Standard tier is listed (no Batch, Flex or Priority) — [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing) (last updated 2026-10-22)
- `gemini-2.5-flash-native-audio-preview-12-2025`: input text $0.50, input audio/video $3.00, output text $2.00, output audio $12.00 — [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)
- Other Live-API endpoints: `gemini-3.5-live-translate-preview` input $3.50 ($0.0053/min), output $21.00 ($0.0315/min audio). `gemini-3.5-transcribe-live` input $3.50 ($0.005/min), output $21.00. `gemini-robotics-er-2-streaming-preview` costs $1.00 input / $5.00 output through 2026-12-31, then $2.00 / $10.00 from 2027-01-01. The translate and transcribe per-minute figures assume 25 audio tokens per second — [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)
- The 3.8 Live row has no footnote explaining its per-minute conversions — [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)
- Per-turn billing: "During each turn, the API bills for all context tokens", including conversation history and system instruction. Charges can be computed from `usage_metadata` — [Vertex best practices](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/live-api/best-practices). Forum threads report costs scaling with turn count rather than call duration, and a staff reply says no context caching applies to Live native audio. Both are forum sources, not docs — [Google AI forum: cumulative prompt tokens](https://discuss.ai.google.dev/t/does-gemini-live-native-audio-bill-cumulative-prompt-tokens-on-every-turn-cost-seems-to-scale-with-turn-count-not-call-duration/173248); [Google AI forum: caching](https://discuss.ai.google.dev/t/title-context-caching-or-cached-input-pricing-for-the-gemini-live-api-native-audio/186850)
- Proactive audio billing (3.8 Live, always on): "Input tokens are billed the entire time the API is listening, and output tokens only when it responds." On 3.1 Flash Live, which has no proactive audio, "you're billed only for audio you actively stream". A "turn" is defined as one user input plus the model's response, for billing purposes — [Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)
- Vertex AI Live pricing was not retrieved (see Gaps).

### Inferences (worked estimate; assumptions explicit, not vendor figures)
Assumptions: `gemini-3.8-live`, Developer API paid tier, 1 hour = 3,600 s, frames at 1 fps, user mic open the whole hour, model speaking 10% of the time (6 min).

1. **If every token were billed once (streaming view):**
   - Video at 70 tokens per frame: 3,600 × 70 = 252,000 tokens × $1.00/M = **$0.25** (at Vertex's 258 TPS: 928,800 tokens = **$0.93**)
   - Audio in at 25 tokens per second: 90,000 tokens × $3.00/M = **$0.27** (per-minute price: 60 × $0.005 = $0.30)
   - Audio out: 360 s × 25 = 9,000 tokens × $12.00/M = **$0.11** (per-minute: 6 × $0.018 = $0.108)
   - **Total ≈ $0.63/hour** (≈ $1.31 at 258 TPS; ≈ $0.53 using the per-minute prices)
   - The $0.002/min image/video price works out to ≈ 2,000 tokens/min ≈ 33 tokens/s. That matches neither 70 tokens at 1 fps (4,200/min) nor 258 TPS, but does match 70 tokens at 0.5 fps (2,100/min). How Google derived it is unexplained.
2. **With per-turn full-context billing (what the Vertex best-practices page states):** the 2-minute audio+video cap forces compression on. With default compression, the context swings between `targetTokens` ≈ 52k and `triggerTokens` ≈ 105k (40% and 80% of 131,072), averaging about 79k. The context grows at about 77 tokens/s (70 video plus the audio activity), so roughly 90% of input tokens are video at $1/M and 10% audio at $3/M, a blended ≈ $1.19/M.
   - One turn every 30 s (120 turns/h): 120 × 79k ≈ 9.4M input tokens ≈ **$11/hour** (+ $0.11 output)
   - One turn every 10 s (360 turns/h): ≈ 28M tokens ≈ **$34/hour**
   - Tight compression (trigger 16k / target 8k, average ≈ 12k), one turn every 30 s: 1.44M tokens ≈ **$1.7/hour**
   - Halving the frame rate to 0.5 fps, or sending frames only on change, roughly halves the video share of these numbers.
3. Takeaway for design: under per-turn billing, cost depends on **context size × number of turns**, not on frame rate alone. Keeping `triggerTokens` low and sending frames only when the screen changes matter more than the per-frame price.

### Gaps
- Whether video tokens already in context are billed again on each turn at the $1/M video rate, whether compression trims what is billed, and how proactive-audio "listening" turns are counted: no official worked example exists. Measure with `usage_metadata` on a real session.
- Vertex AI Live pricing (it can differ from the Developer API) was not fetched.
- Free-tier Live rate limits are not published outside AI Studio.

## Proactive audio, affective dialog and when the model responds to video without a user turn

### Takeaway
On 3.8 Live, proactive audio is **permanently on** (setting it false is an error). As documented, it lets the model *decline* to respond to input it judges irrelevant. It is not described as the model starting to speak on its own when the screen changes. Turns are still driven by audio activity (VAD) or explicit client content. Since Gemini 3.1, video frames sent since the last turn are included in each turn by default (`TURN_INCLUDES_AUDIO_ACTIVITY_AND_ALL_VIDEO`). The docs disagree on affective dialog for 3.8 Live: ai.google.dev says it was removed, Vertex lists it as supported.

### Cited Findings
- `ProactivityConfig.proactiveAudio`: "If enabled, the model can reject responding to the last prompt" — [Live API reference](https://ai.google.dev/api/live)
- Live guide: proactive audio needs `v1beta` and `proactivity={'proactive_audio': True}`, and "the model may decline to respond when content isn't relevant". Affective dialog needs `enable_affective_dialog=True`. "Neither feature is supported in Gemini 3.1 Flash Live" — [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)
- 3.8 Live: "Proactive audio: permanently enabled. Setting `proactive_audio: false` returns an error." "Affective dialogue: removed from the API. Remove any `enable_affective_dialog` settings" — [Gemini 3.8 Live](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live). Vertex lists "affective dialog, proactive audio" among `gemini-3.8-live` features — [Vertex Live API overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api) (conflict).
- Proactive audio is "permanently enabled in `gemini-3.8-live` and `gemini-3.8-live-extended-thinking`", and input is billed for the whole time the API listens — [Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)
- `TurnCoverage`: Gemini 2.5 defaults to `TURN_INCLUDES_ONLY_ACTIVITY`; "Gemini 3.1 and later default to `TURN_INCLUDES_AUDIO_ACTIVITY_AND_ALL_VIDEO`" ("Includes audio activity and all video since the last turn"; with automatic detection, audio activity means speech, not silence). `TURN_INCLUDES_ALL_INPUT` also includes silence — [Live API reference](https://ai.google.dev/api/live)
- `ActivityHandling`: the default is `START_OF_ACTIVITY_INTERRUPTS` (barge-in); `NO_INTERRUPTION` keeps the model's response going when the user speaks — [Live API reference](https://ai.google.dev/api/live)
- A client can inject text or turns at any time: `send_client_content` with `turn_complete=true` interrupts active generation and starts a turn; `send_realtime_input(text=...)` sends realtime text — [Gemini 3.8 Live](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live); [Live API guide](https://ai.google.dev/gemini-api/docs/live-guide)

### Inferences
- For "speak up when something relevant appears on screen", the documented route is client-driven: the client (or the MCP server) detects a screen change and sends a `clientContent` turn ("the screen changed: ...") or a frame plus `turn_complete`. Proactive audio then lets the model stay silent if the change is irrelevant. The model does not watch frames and trigger itself.
- Because 3.8 Live always has proactive audio on and bills listening time, an always-open mic during screen sharing is billed even when nobody speaks.

### Gaps
- No doc describes the model initiating a response from video alone with no audio activity or client turn. I found no source either way.
- Which side of the affective-dialog conflict (removed vs supported on 3.8 Live) is current.

## OpenAI Realtime API (gpt-realtime family and GPT-Live): images, video, cost, limits, tools, MCP

### Takeaway
OpenAI's Realtime API (current model `gpt-realtime-2.1`, after `gpt-realtime-2` of 2026-05-07 and `gpt-realtime` of 2025-08-28) takes **discrete images** as `input_image` conversation items, not a video stream. No model card lists video input. Sessions last at most 60 minutes and have a 128k context. Image input costs $5/M ($0.50/M cached), but the per-image token count for Realtime is undocumented. Remote MCP servers are supported natively and executed by OpenAI's servers. OpenAI's newer GPT-Live (`gpt-live-1`, $0.05/min) is audio and text only.

### Cited Findings
- The Realtime guide's sample uses `gpt-realtime-2.1`. Transports are WebRTC (browser, via `/v1/realtime/calls`) and WebSocket (server). Ephemeral client secrets come from `POST /v1/realtime/client_secrets`. The GA interface drops the `OpenAI-Beta: realtime=v1` header — [OpenAI Realtime guide](https://developers.openai.com/api/docs/guides/realtime)
- `gpt-realtime-2.1`: context 128,000; max output 32,000; knowledge cutoff 2024-09-30; input text, audio and image; output text and audio; video not listed; configurable reasoning effort. Default rate limits: Build 400 RPM / 200,000 TPM; Launch 10,000 RPM / 4,000,000 TPM; Grow 20,000 RPM / 15,000,000 TPM — [gpt-realtime-2.1 model page](https://developers.openai.com/api/docs/models/gpt-realtime-2.1)
- Image input: "`gpt-realtime-2` and `gpt-realtime` also support image input". The image is an `input_image` content part in a user message (`image_url` as `data:image/{format};base64,...`), followed by `response.create`. No size limits, detail levels or token costs are given. "The maximum duration of a Realtime session is 60 minutes" — [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)
- Launch history: on 2025-08-28 OpenAI made the Realtime API GA with `gpt-realtime`, remote MCP servers, image inputs and SIP calling — [OpenAI: Introducing gpt-realtime](https://openai.com/index/introducing-gpt-realtime/) (confirmed via search results; the page returned 403 to direct fetch). `gpt-realtime-2` launched 2026-05-07 with GPT-5-class reasoning, context raised from 32K to 128K, reasoning effort from minimal to xhigh, preambles and parallel tool calls; companion models are `gpt-realtime-translate` and `gpt-realtime-whisper` — [DataCamp](https://www.datacamp.com/blog/gpt-realtime-2); [Notebookcheck](https://notebookcheck.net/openai-launches-three-new-real-time-audio-api-models.1293110.0.html) (secondary sources)
- Pricing per 1M tokens: `gpt-realtime-2.1` and `gpt-realtime-2` cost audio $32 in / $64 out / $0.40 cached, text $4 / $24 / $0.40, image $5 in / $0.50 cached. `gpt-realtime-2.1-mini` and `gpt-realtime-mini` cost audio $10 / $20 / $0.30, text $0.60 / $2.40 / $0.06, image $0.80 / $0.08. `gpt-realtime` and `gpt-realtime-1.5` cost text output $16 and are otherwise the same as 2.x. `gpt-realtime-translate` costs $0.034/min and `gpt-realtime-whisper` $0.017/min — [OpenAI pricing](https://developers.openai.com/api/docs/pricing)
- Audio tokens: user input 1 token per 100 ms (10/s); assistant output 1 token per 50 ms (20/s). "The entire conversation is sent for every Response", so later turns cost more. Prompt caching is automatic and best-effort. When the context overflows, the oldest messages are dropped; `session.truncation.retention_ratio` defaults to 1.0. With VAD on, empty input audio is not counted. The image tokenization rule is not given — [Realtime costs](https://developers.openai.com/api/docs/guides/realtime-costs)
- The generic vision guide does not list realtime models. For reference, its patch-based formula (32 px patches × 1.2) gives 922 tokens for a 1024×768 image and 1104 for 1280×720; the tile-based gpt-4o formula gives 765 and 1105 — [Images and vision](https://developers.openai.com/api/docs/guides/images-vision). Which one applies to Realtime is unknown.
- Function calling: tools are set in `session.update` or `response.create`. The model emits a `function_call` item (`name`, `arguments`, `call_id`); the client sends `conversation.item.create` with a `function_call_output` and then `response.create` — [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)
- Remote MCP: tool `type: "mcp"` with `server_label` and `server_url` (or a legacy `connector_id`), plus `allowed_tools`, `require_approval`, `authorization` and `headers`, at session or response level. "Unlike Realtime `function` tools, remote MCP tools are **executed by the Realtime API itself**." Lifecycle events are `mcp_list_tools.*` and `response.mcp_call.*`. Approval flows through an `mcp_approval_request` answered with `mcp_approval_response`. `response.done` can arrive before MCP calls finish, and the client must send `response.create` itself. `connector_id` "is deprecated for models released after September 1, 2026" (use `server_url` or a Secure MCP Tunnel `tunnel_id`) — [Realtime MCP guide](https://developers.openai.com/api/docs/guides/realtime-mcp)
- GPT-Live: `gpt-live-1` is "a full-duplex voice model" that "can listen and speak at the same time" and delegates reasoning and tools to a backend agent. Input and output are audio and text; image and video are "Not supported". It costs $0.05 per minute billed per second, with backend model and tool usage billed separately. Concurrent sessions: Build 50, Launch 300, Grow 500 (no Free tier). Endpoint `v1/live/sessions`. Function calling is supported — [gpt-live-1 model page](https://developers.openai.com/api/docs/models/gpt-live-1). A search-result summary of the same docs gave "25 at Tier 1 to 500 at Tier 5", which conflicts with the model page; the model page is preferred.
- GPT-Live billing: active time includes user speech, assistant speech, silence and backend work. `POST /v1/live/sessions` bills 15 s at initialization, credited back against duration — [Realtime costs (GPT-Live section)](https://developers.openai.com/api/docs/guides/realtime-costs)

### Inferences
- OpenAI's design is "screenshot as a message" (the client decides when to attach an image), not continuous video. In practice it matches Gemini Live at low fps, with explicit control over which frames enter the context. For a desktop MCP server, `gpt-realtime-2.1` can reach the server directly as a remote MCP server (over the streamable HTTP endpoint) if the server is reachable from OpenAI's infrastructure. That conflicts with this project's loopback-only HTTP runner, so a Secure MCP Tunnel or client-executed function tools would be needed.
- Rough cost of attaching one ~1,000-token screenshot per turn at 120 turns/hour: 120k image tokens × $5/M ≈ $0.60 the first time. Each image is then re-sent with every later response (cached at $0.50/M when the cache hits), so cost grows with conversation length until truncation. This uses an assumed image token count, not a documented one.

### Gaps
- Realtime image token count per image, maximum image size, and any image count limits per session.
- Whether any OpenAI realtime model accepts WebRTC video tracks (none documented). ChatGPT's consumer video is not exposed as an API.

## Other realtime multimodal APIs with video or screen input (Oct 2026)

### Takeaway
Of the others checked, only Alibaba's Qwen Omni realtime documents live image or video frames (about 1 fps, JPEG, ≤256 KB base64), with function calling and remote MCP. Amazon Nova 2 Sonic, xAI Grok Voice, Azure Voice Live and GPT-Live are speech (and text) in only. Azure's "video" is avatar output.

### Cited Findings
- **Qwen Omni realtime (Alibaba Model Studio):** current model `qwen3.8-omni-flash-realtime`, full duplex, accepting text, images, streaming audio and video. WSS endpoint `wss://{WorkspaceId}.{region}.maas.aliyuncs.com/api-ws/v1/realtime?model=...`, plus WebRTC. Frames are sent with `input_image_buffer.append` (Base64 JPG/JPEG). 480p or 720p is recommended, 1080p is the maximum, and "A single image after Base64 encoding must not exceed 256 KB". "We recommend sending images at one frame per second". Audio must be sent before any image. Audio in is 16 kHz PCM16 and out is 24 kHz. Turn detection supports `semantic_vad`, `server_vad` or manual. Custom function calling, remote MCP tools and web search are supported. Pricing and session limits are not on the page — [Alibaba Cloud Model Studio: Realtime](https://www.alibabacloud.com/help/en/model-studio/realtime)
- **Amazon Nova 2 Sonic:** speech-to-speech over Bedrock bidirectional streaming. Cross-modal input is "audio and text inputs". It supports asynchronous tool handling ("continue speaking while tools process in the background") and has a "Connection limit of 8 minutes" with a renewal pattern. No image or video input is listed — [AWS Nova 2 user guide](https://docs.aws.amazon.com/nova/latest/nova2-userguide/using-conversational-speech.html); [AWS announcement, Dec 2025](https://aws.amazon.com/about-aws/whats-new/2025/12/amazon-nova-2-sonic-real-time-conversational-ai)
- **xAI Grok Voice:** the realtime API reuses OpenAI Realtime protocol event types, with models such as `grok-voice-latest` — [Pydantic AI xAI realtime docs](https://pydantic.dev/docs/ai/realtime/xai/). The voice agent is priced from $0.05/min per a search summary of xAI docs — [xAI docs overview](https://docs.x.ai/overview). No image or video input in the voice session was found.
- **Azure Voice Live:** one WebSocket endpoint for several models (for example `gpt-realtime`) selected by query parameter, plus WebRTC avatar streaming "with video, animation, and blendshapes" (`session.avatar.connect`). That is avatar output; no user video input is documented — [Azure Voice Live API reference 2026-04-10](https://learn.microsoft.com/azure/ai-services/speech-service/voice-live-api-reference-2026-04-10)
- **OpenAI GPT-Live:** image and video "Not supported" — [gpt-live-1](https://developers.openai.com/api/docs/models/gpt-live-1)
- **Gemini Live avatars:** Vertex lists "Live avatars: video (mp4)" as an output for `gemini-3.8-live`; this is also output, not input — [Vertex Live API overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api)

### Inferences
- The industry settles on the same pattern: about 1 fps stills over the voice socket (Gemini, Qwen) or images as discrete messages (OpenAI). None of these APIs offers true video streaming for screen input as of October 2026.

### Gaps
- Mistral (Voxtral realtime) was not researched. It is known as speech-to-text, but this was not verified for this note.
- Qwen Omni realtime pricing per image and session limits; xAI's official voice API reference was not fetched directly.

## Consumer products built on these: Gemini Live, ChatGPT and Copilot Vision screen sharing

### Takeaway
The consumer products confirm the "session-scoped, user-started, frames or page content on demand" pattern. None publishes a frame rate. Copilot Vision says the screen is "processed as a series of images" and "can't take action"; Gemini in Chrome shares the tab's page content rather than describing pixels; ChatGPT's video and screen share is a mobile Advanced Voice feature.

### Cited Findings
- **Copilot Vision (Microsoft):** "Shared screen or camera content is processed as a series of images". It "can't take action or directly manipulate items on your screen", cannot read videos or animated GIFs, works only in voice chats, and quickly switching windows can produce answers about the wrong screen. It is user-started and session-bound ("no long-term recall", no reuse of earlier screens). Audio and video are kept 48 hours for feedback, then deleted. Desktop sharing works on Windows or the web. No frame rate is given — [Microsoft support: How vision in Copilot works](https://support.microsoft.com/en-au/microsoft-365-copilot/how-vision-microsoft-365-works)
- **Gemini in Chrome "Go Live" (desktop):** "This shares the page content from the tab you're on". The user can share "up to 10 of your recent open tabs". While shared, the page edges glow and the tab shows a glowing underline. Sharing can be paused, and navigating within a shared tab means "Gemini uses the new page". Whole-screen sharing is not described — [Chrome Help: Go Live with Gemini in Chrome](https://support.google.com/chrome/answer/16363185?hl=en)
- **Gemini Live on Android:** screen and camera sharing became free for all Android users (2025) — [Chrome Unboxed](https://chromeunboxed.com/gemini-live-screen-and-camera-sharing-is-now-free-for-all-android-users/)
- **ChatGPT:** video and screen sharing in Advanced Voice Mode launched in December 2024 on iOS and Android for paid tiers — [VentureBeat](https://venturebeat.com/ai/chatgpt-gets-screensharing-and-real-time-video-analysis-rivaling-gemini-2). OpenAI's help center (per search summary; direct fetch returned 403) says video sharing is on the iOS and Android apps through the camera button, screen sharing through the "..." menu and "Share Screen", and that a newer "Live" voice did not support video or screen sharing at launch — [OpenAI Help: Voice conversations](https://help.openai.com/en/articles/8400625-voice-conversations-beta)

### Inferences
- Chrome's Go Live sends DOM or page content, not pixels, which parallels this project's `browser_page_text`/`browser_find` approach. Google's own desktop product prefers structured page content over frames when it can get it.
- Copilot's warning about switching windows shows that frames are sampled around the moment of the question, not continuously, which matches the VAD-gated sampling seen in LiveKit.
- The visible "being shared" cues (Chrome's glow, Copilot's stop control) parallel this project's status card.

### Gaps
- No consumer product publishes its frame rate or capture trigger. ChatGPT's desktop app screen-share status in October 2026 was not confirmed.
